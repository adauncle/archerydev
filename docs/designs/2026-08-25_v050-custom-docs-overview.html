1. 核心约束（8/24 拍板 3 条硬规则）

✅ 约束 1 · 只 DBA 上传

设计规范 / 运维手册所有权 100% 在 DBA 团队，业务 RD 不上传不删除不编辑

业务用户只读，避免"多个人改同一个文件" 冲突

✅ 约束 2 · 完全不绑定

跟库 / 表 / SQL 工单无任何外键关联，纯平台文档库

类似百度网盘内部版，不是 Notion/Confluence

✅ 约束 3 · 5 种文件类型

Markdown / HTML / PDF / Word / Excel

覆盖 DBA 日常维护场景（规范/扫描件/外审报告/巡检报表/富文本）

2. 业务痛点 & 收益（为什么做）

现状（8/24 `/dbaprinciples/` 修过的那个页面）

  • 当前 /dbaprinciples/ 硬编码读 docs/docs.md 单文件，❌ 业务用户只能看不能维护
  • DBA 加新规范要改代码走部署，一改就是 1 小时
  • 文档内容跟平台代码绑死，跟其他平台模块解耦度 0

业务收益估算

指标现状上线后
DBA 维护文档耗时1 小时/规范/季度（走代码）10 分钟/规范/季度（走平台）
业务 RD 查规范耗时1-2 小时（问人 + 找文件）5 分钟（平台搜索）
重复咨询次数20+ / 周5 / 周
新人入职培训1 对 1，半天自助式，1 小时

Phase 2（v0.5.1 增强，1 周）

  • 文档版本管理 / 批量上传 / 收藏 / 评论

不做（out of scope，明确划线）

❌ Office 完整编辑

只能预览不能编辑（避免 LibreOffice 集成坑）

❌ 在线 Markdown WYSIWYG

DBA 本地写好再上传（避免前端编辑器坑）

❌ 全文搜索（ES）

标题/描述/分类模糊匹配够用，ES 集成过重

❌ 跟 SQL 工单绑定

用户拍板不绑定，保持简单

4. 权限模型（5 个 perm，跟 8/24 gh-ost 同样套路）

角色拥有的 perm行为
业务 RD（默认）view_document列表 / 详情 / 下载（只读）
DBA（在 DBA 组）view_document upload_document change_document delete_document view_document_audit全部 + audit log
业务 RD leaderview_document只读
Admin（is_superuser）全部全部 + admin 后台
⚠️ 8/24 教训复用：端点 perm 守卫 不能 raise PermissionDenied（会返整页 HTML，AJAX 拿到源码 alert 弹源码），必须返 JsonResponse({"ok": False, "error": "..."}, status=403)

5. 文件存储 & 5 预览方案

存储路径

/opt/archery/shared/uploads/documents/<uuid>.<ext>

uuid 避免冲突 + 不暴露原始文件名 + 下载时用 title + 扩展名

5 种类型预览前端方案

类型预览方案前端库
Markdown渲染为 HTMLmarked.js + DOMPurify（XSS 防护）
HTMLiframe 沙箱原生 iframe + sandbox 属性
PDF浏览器原生pdf.js（兼容旧浏览器）
Word转 HTML 显示mammoth.js（client 端解析）
Excel表格预览sheetjs（xlsx 解析）

8. 关键风险（必看）

🔴 风险 1 · 文件类型解析失败

PDF / Word / Excel 用 client 端库解析失败时显示"下载"提示

Mammoth.js / sheetjs 对复杂格式支持有限，不能保证 100% 完美预览

🟡 风险 2 · 文件上传大小限制

PDF 扫描件可能 10+ MB，默认 20MB 上限

超过给清晰提示，DBA 自己压缩或拆文件

🟡 风险 3 · 病毒文件上传

Archery 平台无病毒扫描，DBA 内部使用风险低

如果对外开放需加 ClamAV 集成（Phase 2 考虑）

🟢 风险 4 · 已解决

权限细分 / 软删除 / audit log / 跟 SQL 工单解耦 — 设计稿都已覆盖
