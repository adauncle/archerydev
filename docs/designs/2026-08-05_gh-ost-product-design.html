01为什么需要无锁 DDL

在 Archery 里提交 DDL 工单（如 ALTER TABLE users ADD COLUMN age INT），底层默认走 原生 ALTER TABLE，会锁表。

传统 ALTER TABLE

100GB 用户表加字段
→ 锁表 2~8 小时
→ 期间所有读写全部卡住
→ 用户登录失败、订单丢失

→

gh-ost 无锁

100GB 用户表加字段
→ 创建影子表 + 增量同步
→ 业务读写 零中断
→ cut-over 切换，几秒延迟

gh-ost 是 GitHub 开源的 MySQL 在线改表工具。要在 Archery 里集成它做"无锁模式"。

谁会用到：DBA 团队 100% 用得到（不用 gh-ost 改不了大表）。业务开发偶尔用（一般表 < 1GB 用传统方式就够）。

02用户故事：3 个角色

小
小李（业务开发）
前端工程师，给 orders 表加 status 字段

orders 表有 8000 万行，下午 3 点想加个 status 字段。直接 ALTER 会锁表，业务高峰顶不住。我希望提交工单时勾一下"无锁模式"，Archery 帮我后台慢慢改，**我下班前看进度面板**就行。

王
王 DBA
审核 + 监控 DDL 工单

每天 20+ 个 DDL 工单，**大表占 10%**。我审核时希望：1) 看到表大小；2) 看用户选了无锁没；3) 跑失败时能手动重试或回滚。**默认开启 "ALTER_TABLE_LOCK_WAIT_TIMEOUT" 监控**——传统 ALTER 跑超过 30s 自动告警给我。

SRE
SRE 老张
管 Archery 平台 + 服务器

gh-ost 是装在 110 PROD 的二进制，跑起来占 CPU/IO。**每个工单一个 systemd 临时 unit**（systemd-run --scope），跑完自动销毁。如果 gh-ost 自己挂了，**systemd 5s 重启**或**保留 task 状态**让人工查。我不想要"孤儿进程"。

05预检查：什么能用什么不能

用户勾"启用 gh-ost" → 提交瞬间 Archery 自动跑预检查（~5s）。**全部通过才真跑 gh-ost**，否则弹窗告诉用户哪条不通过。

✓ 启用 gh-ost 的条件

  • 实例 binlog_format=ROW（gh-ost 必需）
  • 磁盘剩余 ≥ 1.2 × 表大小
  • 账户有 REPLICATION SLAVE、REPLICATION CLIENT 权限
  • SQL 是 ALTER TABLE，不是 RENAME、DROP、TRUNCATE
  • 目标表非 分区表、非临时表

✗ 禁用 gh-ost 的情况

  • 改主键 / 改索引类型 / 全文索引
  • binlog_format=STATEMENT 或 MIXED
  • GTID 模式不一致（多源复制）
  • 外键约束 + 引用此表的其他表
  • 表大小 < 1GB（建议走传统 ALTER）

预检查失败时：工单不让提交 + 明确告诉用户哪条不通过 + 建议改用传统 ALTER 或找 DBA 处理。不会"看似跑了 gh-ost 其实跑挂了"。

08DBA 视角：异常处理

所有 gh-ost 任务在 admin 多一个列表页，所有异常都进这里，DBA 不会漏看。

prodarchery.ahggwl.com:9123/admin/ext_ddl_ghost_task/
ID工单实例 / 表状态进度开始操作
#4821 #4698 prod-mysql-01 / orders running 67% 15:32 查看 · 取消
#4820 #4685 prod-mysql-02 / users done 100% · 18 min 15:14 详情
#4818 #4665 prod-mysql-01 / logs failed 31% · 磁盘满 14:22 查看 · 重试 · 回滚

DBA 一键操作

取消：发 SIGTERM 给 gh-ost，影子表立即清理。
重试：用相同 SQL 重启 gh-ost（从 queued 重新开始）。
回滚：rename 影子表为原表名，砍掉已改的表结构。

影子表回收

每天凌晨 3 点 cron 扫 ext_ddl_ghost_task，
completed 超过 24h 的任务 → DROP _ghc_del_xxx。
失败任务的影子表保留 7 天供排查。

09安全设计：怎么不翻车

  • 默认关闭：用户不勾选 = 走传统 ALTER（行为不变，向后兼容）
  • 预检查拦 5 道：binlog_format / 磁盘 / 权限 / SQL 类型 / 表类型，任何一条不过不让跑
  • systemd 临时 unit：每个任务一个 systemd-run --scope=ghost-<audit_id>，跑完自动销毁，孤儿进程自动清理
  • cut-over 时机由 DBA 控制：可选"业务低峰切换"模式（默认立刻切），可指定时间窗（如 02:00-04:00）
  • 影子表保留 7 天：cut-over 失败时人工回滚的最后机会
  • 暂停阈值：threads_running > 30 自动暂停 gh-ost（避免压垮生产）
  • 超时熔断：超过 2h 未完成自动停止 + 告警 DBA
  • 灰度开关：v0.3.0-alpha 阶段只对标记为"灰度用户"的账号开放

cut-over 是关键时刻（rename 阶段，几秒锁表）。生产环境默认在业务低峰期切（22:00 后），可配"自动 cut-over 时间窗"。紧急情况 DBA 手动触发立即切。

103 阶段交付计划

每个阶段独立可发布，建议按顺序。每个迭代约 1 周。

  1. v0.3.0-alpha · 骨架阶段
    预检查 + 任务模型 + UI 框架
    • 装 gh-ost 二进制到 134 dev + 110 prod（systemd-run 跑临时 unit）
    • 新建 ext_ddl_ghost_task 表（task 状态 / 进度 / 错误 / stdout 历史）
    • 预检查 5 道：binlog_format / 磁盘 / 权限 / SQL 类型 / 表类型
    • 工单详情页加 checkbox + 进度面板（polling 3s）
    • 预检查失败弹窗 + 明确告诉用户改用传统 ALTER
    • 不真跑 gh-ost，只生成 task 记录（标记 "would use gh-ost"）
  2. v0.3.0-beta · 执行阶段
    真跑 gh-ost + 实时进度
    • 用户勾 gh-ost → Archery 调 gh-ost 二进制 + systemd-run
    • 后台轮询 gh-ost stdout（3s）→ 解析 Copy: 12345/100000 rows → 写 task.progress
    • 状态机：queued → connecting → copying → cut-over → done / failed
    • DBA admin 多一个 ext_ddl_ghost_task 列表页（取消/重试/回滚）
    • 完成/失败 → 钉钉群通知（依赖 v0.2.1 OA 框架）
    • cut-over 时机：默认立刻切 / 可配"低峰期时间窗"
  3. v0.3.0 · 完整版
    pt-osc 兼容 + 影子表清理 + 上线 runbook
    • 老 MySQL 5.6/5.7 实例支持 pt-osc（默认收起"高级"tab，灰度用户）
    • 影子表 _ghc_del_xxx 24h cron 自动清理
    • 完整 e2e：演练大表（你公司 100GB+ 业务表）
    • 上线 runbook + 故障排查手册
    • 性能基准测试报告（cut-over 延迟、CPU/IO 峰值）

11验收标准

v0.3.0-beta 阶段需要全部满足：

  • 提交 100GB+ 表的 ALTER TABLE ADD COLUMN 工单，勾"启用 gh-ost" → 业务读写零中断（监控 30 分钟无超时错误）
  • 进度面板每 3 秒刷新，显示 已复制行数 / 速度 / 当前阶段 / 线程负载
  • cut-over 自动完成后，业务开发收到钉钉通知（含工单号 / 耗时 / 影响行）
  • DBA 在 admin 可看所有 task，可一键取消/重试/回滚
  • 预检查 5 道任一不通过 → 弹窗明确告诉用户，不静默
  • gh-ost 自己挂了 → systemd 5s 重启，超过 2h 自动停止 + 告警
  • 影子表 24h 后 cron 自动清（不污染数据库）
  • 灰度阶段只对"灰度用户"开放，避免一上来全公司都能用
