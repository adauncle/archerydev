背景 · 为什么开发这个功能

当前两个流程 → 痛点 → 影响 → 新功能目标, 4 部分讲清楚必要性。

① 当前数据同步到历史库 · 两个流程

DML 数据同步: 科大国创数据同步组件 · 按时间戳增量 · T+1 增量同步 · 业务 RD 不参与

DDL Schema 同步: 无工具, 纯人工 · DBA 凭经验判断 · 人工到历史库跑 SQL

→ DML 走自动化组件没问题, DDL 走人工是当前最大风险。本设计稿解决的就是 DDL 人工同步的问题。

② 痛点 · DDL 人工同步 5 个具体问题

1 · DBA 漏同步 (每天 DDL 工单 5-20 条, 凭记忆判断) — 高

2 · 没有自动校验 (业务库 DDL 跑通 ≠ 历史库 DDL 跑了) — 高

3 · 同步不及时 (DBA 下班前集中处理, 延迟 4-8h) — 中

4 · 跨业务库多库容易配错 (hly_accesscard / hly_activity / hly_doc_model) — 中

5 · DML 同步依赖 DDL 先同步 (历史库没 DDL → 科大国创整条挂) — 高

当前流程图 (R 之前 · DBA 视角) + 优缺点

业务 RD ──①提 DDL 工单──▶ DBA ──②凭经验判断──▶ DBA ──③手工到历史库跑 SQL──▶ 历史库
维度当前 (R 之前)
✅ 优点DML 走科大国创组件, 自动化 T+1 增量同步
❌ 缺点 1DDL 走 DBA 人工, 凭经验判断, 容易漏 (每天 5-20 条)
❌ 缺点 2没有"两边 schema 一致" 强制校验, 漏了没人发现
❌ 缺点 3DBA 下班前集中处理, 同步延迟 4-8h
❌ 缺点 4跨多库场景容易配错目标库 (hly_accesscard / hly_activity / hly_doc_model)
❌ 缺点 5DML 同步依赖 DDL 先同步, DDL 漏 → DML 整条挂

③ 影响 · DDL 漏同步的真实业务影响链路

T+0 当天: 业务库 DDL 跑通 · 业务 RD 不知道历史库没同步 (DML 在偷偷失败重试)

T+1 第二天: 科大国创 DML 同步任务整体失败 (e.g. 业务库加字段, 历史库没, INSERT 报错, 整条挂)

T+1 ~ T+3: 下游大数据 (数据仓库 / 报表 / 风控 / 决策支持) 读历史库, "昨天数据没进来" / "缺字段" / "JOIN 失败"

T+3+: 业务方反馈"报表数据延迟" / "数据缺漏" / "对账不平", 反查才发现是历史库 DDL 没同步

DBA 介入: 手动补执行历史库 DDL + 手动重跑 DML 同步任务, 修复 1-4h · 下游数据延迟 1-3 天

📌 真实案例 (实战): 业务库 hly_doc_model 7.28M rows test 表 gh-ost 改字段 · 历史库 DDL 漏同步 → 科大国创整条同步链路挂 · 下游数据仓库延迟 2 天, 业务方反查才暴露

④ 新功能 v0.5.0 DDL 跨库同步 · 解决什么痛点, 达成什么目标

新功能一句话: 业务库 DDL 审过 → Archery 自动在历史库生成镜像 DDL 工单 → 走当前配置的流程 (跟正常历史库工单一样, R3 拍板)

解决的痛点 (对应 ② 5 个):

· 痛点 1 漏同步 → 业务库 DDL 审过自动触发历史库镜像工单 · 0 漏同步

· 痛点 2 没校验 → 业务库 DDL 必审过 (current_status=1 PASSED) 才触发 · 实时校验

· 痛点 3 不及时 → T+0 实时触发, 不再下班前集中处理

· 痛点 4 跨多库配错 → DBA 配库对时 WHERE TABLE_SCHEMA LIKE 'hly%' 跨多库, 一次配多业务库多历史库

· 痛点 5 DML 同步挂 → DDL 0 漏同步 → DML 同步永久稳定 (科大国创不再因 DDL 漏同步挂)

达成的 5 个目标:

1 · DDL 0 漏同步 — 不再依赖 DBA 人工记忆

2 · 下游大数据 0 延迟 — DDL T+0 同步, 业务方无感知

3 · DBA 配表 1-click 完成 — 一键配机制 (业务库 1589 / 历史库 1289 实战数据 6 min 配完, R2)

4 · DML 同步永久稳定 — 历史库 schema 跟业务库永远 1:1 同步

5 · 历史库工单跟正常工单一样 — 0 额外代码, DBA 改"历史库组" 流程就生效 (R3)

🔄 v0.5.0-r3 重大决策变更 — 走当前配置的流程

这是个优雅的设计原则 — 自动生成的历史库镜像工单跟正常历史库工单走一样的审计流, DBA 改 Archery 配置就生效, 0 额外代码。

🎯 决策核心

自动生成的历史库镜像工单走当前 Archery 配置的流程 (workflow_audit_setting.audit_auth_groups):

  • 0 额外代码, 0 重复配置, 复用现有 SqlWorkflow + audit_setting 机制
  • DBA 改 "prod core for 历史库" 组的流程 (单级 / 双级 / 加 leader), 镜像工单自动跟进
  • v0.5.0 代码不写"由谁审" / "走几级", 完全用 Archery 现成配置

📊 R1 vs R3 拍板对比

维度 R1 拍板 (作废) R3 拍板 (采用)
审批人 同业务库 DDL 审批人 (3 级) 按当前 Archery 配置 (DBA 配的) 走
业务库 DDL 没审过怎么办 没明确 不联动 (业务库 DDL 必审过)
业务 RD 收到通知 RD + leader 都收 (重复) 只通知 RD (不重复打扰 leader)
实施复杂度 需单独为"自动生成" 写代码 0 额外代码, 复用现有 audit_setting

✅ 3 实施原则

1. 镜像工单跟正常工单一样 — v0.5.0 代码不写"由谁审" / "走几级"

2. 业务库 DDL 必审过 (current_status=1 PASSED) 才触发镜像工单 — trigger 加 if source_workflow.current_status != 1: return None

3. 业务 RD 实时通知 (钉钉 OA) — 业务库 DDL 触发镜像工单时, 钉钉通知业务 RD: "你的 DDL #12345 触发了历史库工单 #12346"

🛡️ 3 安全护栏

1. 业务库 DDL 必审过 trigger — 跟实施原则 2 一致 (底线)

2. 历史库执行前预演 + 异常 rollback — 跟 v0.4.5 智能回滚 联动 (R 之前拍板, 已落地)

3. 异常通知 DBA + 业务 RD — 跟 v0.2.0 钉钉 OA 联动, 异常立刻钉钉通知

⚙️ Archery 配置 (DBA 后台自己配, v0.5.0 不动)

工单类型: SQL 上线申请
