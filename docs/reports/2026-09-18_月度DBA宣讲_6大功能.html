功能 ①

字段 diff 弹窗

改一个列，告诉你动了哪些
😰
痛点
业务方提交 ALTER TABLE，Inception 只说"语法 OK"，但没说"动了哪些列、丢了哪些索引"。上线后才发现改动影响范围超出预期。
✨
优势
改表前自动弹出本次 DDL 影响的所有列和索引，新增/修改/删除三色高亮，业务方一眼看清改动。
📖
怎么用
业务方在 SQL 编辑框提交后，弹窗自动展开，无需任何额外操作。点击"对比"还能看 before/after。
📌 实战案例（DBA-bug-1 + DBA-bug-8）
业务方提交 ALTER TABLE ... ADD INDEX idx_owner_name (owner_name)，弹窗立刻显示"索引 idx_owner_name 已存在"，业务方才知道这是重复索引（9/16 DBA-bug-8 实战新增）。

功能 ② ⭐9/17 加 v0 智能模式

大表无锁变更 + v0 智能模式

业务方 0 感知 · 智能分流大小表 · DBA 不蹲守
😰
痛点
大表 ALTER 默认InnoDB 锁表 5-30 分钟，业务方写入全阻塞；多 ALTER 大小表混合工单业务方必须手动选 gh-ost/原生。
✨
优势
gh-ost 通过 binlog + 影子表实现无锁 DDL，v0 智能模式自动分流（大表 gh-ost + 小表原生 ALTER），业务方什么都不用选。
📖
怎么用
业务方勾选"启用 gh-ost 无锁变更"（自动判断：100MB 或 10 万行），多 ALTER 工单选 smart 模式即可，系统自动分流。

功能 ③ ⭐9/17 加多 ALTER 支持

历史库自动同步 + 多 ALTER 黑/白名单

改了主库不用改历史库 · 多 ALTER 零丢失
😰
痛点
改了主库忘改历史库 → 3 个月后查历史库发现表结构对不上；多 ALTER 工单白名单/黑名单只判定第一张表，其他表被丢掉。
✨
优势
主库 DDL 自动同步到历史库镜像工单。9/17 新增每条 ALTER 独立判定白/黑名单，skipped ALTER 写 history，kept ALTER 拼新 SQL 创建镜像工单。
📖
怎么用
业务方什么都不用做——主库改完后 Archery 自动开历史库镜像工单，DBA 审批即可。即使 8 条 SQL 混合工单也零丢失。
📌 实战案例（wf#4841 形态 + 9/17 e2e）
业务方工单含 8 条 SQL（4 CREATE + 4 ALTER），黑白名单混合。DDL-Sync-Bug-A 修后：黑名单的 2 条 ALTER 写 DdlSyncHistory(skipped)，白名单的 2 条 ALTER 拼成镜像工单（只含这 2 条，不带黑名单）。110 prod 镜像工单 #4859 实战验证。
07 / 11
功能 ④ ⭐本月新

跨库直接拒绝

一个工单只能改一个库 · 提交时拦截
😰
痛点
业务方 select A 库，SQL 写了 B 库的表——Inception 只检测语法不判定库归属。上线后才发现改错库，紧急回滚。
✨
优势
检测到跨库 SQL →红框 alert + 提交按钮 disabled + 文案"请先修复跨库"，业务方第一眼就知道改错了。
📖
怎么用
业务方照常提交工单即可，系统自动检测。如果跨库，弹红框 + 按钮变灰，改对 SQL 后按钮自动恢复。
📌 实战案例（9/16 业务方实测 wf#4821）
业务方提交 SQL 混合了两条：ALTER hly_accesscard.t1 + ALTER hly_usercenter.t2。Archery 立刻弹红框"SQL 涉及库 ['hly_usercenter'] 跟您选的库 hly_accesscard 不一致"，按钮变灰。改对后正常提交。
08 / 11
功能 ⑤ ⭐本月新

INSERT 重复 PK？提交时就告诉你

主键冲突预检 · 不再等报错返工
😰
痛点
业务方 INSERT 15 条，其中 6 条 PK 跟前面重复。Inception 不查 DB 现有 PK 值，等执行到第 N 条才发现 Duplicate entry，浪费 14 条 approve 工单流。
✨
优势
提交时直接查 DB 现有 PK 值，发现重复 →红框 alert + 提交按钮 disabled，列出具体冲突的 PK 值和行号。
📖
怎么用
业务方照常提交即可。如果有 PK 冲突，弹窗显示具体哪些值冲突，业务方改 SQL 后按钮自动恢复。
📌 实战案例（9/16 业务方实测 wf#4834）
业务方 INSERT id 302-311 共 15 条，其中 306/307/308/309 重复。Archery 弹红框"PK 值 [306, 307, 308, 309] 在 output_fee_config 表中已存在"，按钮变灰。业务方改对后再提交。

功能 ⑥ 🔥9/17 双重大事故闭环

v1 混合 DDL 禁止 + DBA-bug-10 CREATE INDEX

两个子功能组合 · 0 误报 0 漏报 · wf#4841/wf#4849 实战闭环
🆔
子功能 A — v1 混合 DDL 禁止提交
痛点（wf#4841）：业务方工单含 4 CREATE + 4 ALTER，旧"提醒"模式无效，业务方无视 banner 继续提交，工单显示"成功"但实际 7/8 失败（CREATE 全部丢失）。

修法（前后端双层防护）：
• 前端：检测回调加 mixed_ddl 红框 + 提交按钮 disable
• 后端：WorkflowContentSerializer.create() 第一步 raise ValidationError
• 错误优先级：mixed_ddl > cross_db > pk_conflict

演练：8/8 case PASS（含 wf#4841 实战），134 dev + 110 prod 双向验证
⚡
子功能 B — DBA-bug-10 CREATE INDEX 等价 ALTER
痛点（wf#4849）：业务方 CREATE INDEX test USING BTREE ON hly_accesscard.accesscard_channel_task (req_url) 操作170 万行表，绕过所有 ALTER 检测（大表 alert / gh-ost / 字段 diff / 镜像工单）。

修法（5 文件统一）：
• sql/views.py + ddl_gh_ost/views.py + ddl_sync/sync_trigger.py + sqlsubmit.html + column_diff.py
• CREATE INDEX ⇔ ALTER TABLE ADD INDEX，统一识别

演练：10/10 case PASS + 110 prod 大表演练 rows=1707167 / size_mb=865.4
