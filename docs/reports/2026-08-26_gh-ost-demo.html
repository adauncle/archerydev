1 业务 RD 提交 DDL 的痛点

❌ 痛点 1:大表 ADD COLUMN 锁表 5-10 分钟

业务 RD 给 accesscard_black_detail (144MB) 加一列,MySQL 原生 DDL 直接锁表。

  • 锁表期间: 业务全部 INSERT/UPDATE/SELECT 都卡住
  • 客户端超时: 应用层报错"Lock wait timeout exceeded"
  • 业务影响: 早高峰报错率 0.5% → 12% 飙升
  • 用户投诉: DBA 群里@业务 RD"赶紧回滚"

❌ 痛点 2:凌晨运维窗口抢时间

业务 RD 只能选凌晨 2-5 点低峰期提单,DBA 熬夜值守。

  • 业务抱怨: "变更太慢影响新功能上线"
  • DBA 抱怨: 每天凌晨值班 1-2 个工单,白天其他工作被打断
  • 风险: 凌晨人为操作失误概率高 3 倍
  • 扩展性: 业务增长 → 凌晨窗口不够用
根因: MySQL 5.7 及之前所有 ALTER TABLE 都是在线阻塞,8.0 INSTANT/INPLACE 也只覆盖部分场景(ADD COLUMN 可以 INSTANT,但 MODIFY COLUMN / DROP COLUMN 还是会锁表)。 gh-ost 是 GitHub 开源的成熟方案,binlog 异步重写 + cut-over 切表,业务 0 中断。

2 解决方案:gh-ost + 业务前端 3 按钮

Archery 集成 gh-ost 后,业务 RD 提单流程不变,只是在 SQL 提交页看到 3 按钮提示:

1

自动识别大表

提交页调 goInception 查 information_schema.tables 拿 DATA_LENGTH + INDEX_LENGTH。阈值默认 16MB。

2

3 按钮防呆

大表 DDL 显示 3 选项:启用 gh-ost / 立即执行(接受锁表) / 终止工单。默认推荐 gh-ost。

3

gh-ost 进度面板

启用后写 ext_ddl_ghost_task 任务,启动 gh-ost 进程,前端 3s 轮询进度,显示 cut-over 阶段。

4

任务管理 + 取消/重试

任务列表页(/gh_ost/admin_list/)显示所有 gh-ost 任务,支持 cancel/retry,DBA 可全权兜底。

核心差异:业务 0 中断

对比项 MySQL 原生 DDL gh-ost (Archery 集成)
锁表时间 (144MB 表 ADD COLUMN) 5-10 分钟 (业务卡死) 0 秒 (原表只读 0.5s,cut-over)
回滚能力 无 (DDL 一旦执行不能中断) 完整 (切表前可中断,影子表丢弃即可)
大表延迟 主从延迟 5-10 分钟 主从延迟 <3s (chunk size 1000 行/批)
运维窗口 必须凌晨 2-5 点 随时可执行
运维成本 DBA 熬夜值守 DBA 看任务列表确认即可

3 实操演示 4 步走

步骤 1:业务 RD 提交大表 DDL

业务 RD 在 SQL 提交页选 instance,选数据库 archery_dev,写 DDL:

172.20.2.134:9003/sqlsubmit/

SQL 上线   ›  提交

SQL 上线 · 提交

目标实例 测试 MySQL 8.0 (127.0.0.1:3306)
目标数据库 archery_dev
SQL 内容 ALTER TABLE accesscard_black_detail ADD COLUMN card_type TINYINT DEFAULT 1 COMMENT '卡类型';
⚠️ 检测到大表 DDL
表 archery_dev.accesscard_black_detail 占用 144.0 MB (DATA_LENGTH + INDEX_LENGTH),
超过大表阈值 16MB。原生 DDL 锁表预计 5-10 分钟,业务将中断。

推荐使用 gh-ost 无锁变更 (业务 0 中断)。

步骤 2:启用 gh-ost,写任务

业务 RD 选"启用 gh-ost",Archery 后端做 3 件事:

  1. 写 ext_ddl_ghost_task 记录(任务表,DB 持久化)
  2. 调 runner.build_ghost_command 拼 gh-ost CLI 参数
  3. Popen 启动 gh-ost 进程,worker 异步执行
# ext_ddl_ghost_task 写入
task = DdlGhostTask.objects.create(
    workflow=workflow,           # 关联 SQL 工单
    task_type="ghost",
    db_name="archery_dev",
    table_name="accesscard_black_detail",
    alter_statement="ADD COLUMN card_type TINYINT DEFAULT 1",
    instance=instance,
    status="running",
    enabled=True,
    created_by=request.user.username,
    max_load_threads_running=30,
    timeout_seconds=7200,
)

# gh-ost CLI 启动 (拼出来大概长这样)
gh-ost \
  --host=127.0.0.1 --port=3306 \
  --user=archery --ask-pass \
  --database=archery_dev \
  --table=accesscard_black_detail \
  --alter="ADD COLUMN card_type TINYINT DEFAULT 1" \
  --allow-on-master \
  --execute \
  --chunk-size=1000 \
  --max-load="Threads_running=30" \
  --max-lag-millis=1500 \
  --cut-over=atomic \
  --cut-over-lock-timeout-seconds=3 \
  --default-retries=120 \
  --verbose \
  --sock=/tmp/gh-ost.archery_dev.accesscard_black_detail.sock

步骤 4:验证表结构 + 数据完整性

gh-ost 完成后,业务 RD 在 Archery 走 SQL 查询验证:

-- 1. 看表结构 (新列已加上,其他列不变)
SHOW CREATE TABLE accesscard_black_detail\G

-- 2. 看新列默认值 (DDL 子句生效)
SELECT id, card_type FROM accesscard_black_detail LIMIT 3;
-- +----+-----------+
-- | id | card_type |
-- +----+-----------+
-- |  1 |         1 |  ← DEFAULT 生效
-- |  2 |         1 |
-- |  3 |         1 |
-- +----+-----------+

-- 3. 数据行数 (没丢数据)
SELECT COUNT(*) FROM accesscard_black_detail;
-- 241558 ← 跟 gh-ost 复制行数一致

-- 4. COMMENT 业务描述保留 (8/13 拍板关键点)
SHOW FULL COLUMNS FROM accesscard_black_detail WHERE Field='card_type';
-- Field    | Type      | Null | Key | Default | Comment
-- card_type | tinyint(4) | YES  |     | 1       | 卡类型   ✓
验证通过:表结构 OK + 新列已加 + 数据完整 (241558 行一致) + 业务描述保留。 整个变更业务 0 中断(只 cut-over 阶段 0.5s 原表只读)。
