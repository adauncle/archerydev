优先级 2

优先级 3
🔑 pk_conflict
INSERT 主键重复 → 必须改 PK 值

smart
⭐ 推荐（90% 场景）
系统自动判断每张表的大小：
< 100MB 且 < 10 万行 → 原生 ALTER
≥ 100MB 或 ≥ 10 万行 → gh-ost
⭐⭐⭐
all_ghost
运维场景
强制所有表都走 gh-ost
（小表也走 gh-ost，浪费时间）
⭐
all_native
DBA 已评估
强制所有表都走原生 ALTER

⭐⭐

关键经验

5 条实战经验，让开发少走弯路

这些不是产品介绍，是 DBA 实战打出来的
经验 1: 字段 diff 弹窗 = 你提交前最后一道防线
触发条件：含 ALTER TABLE / CREATE INDEX 的 SQL
什么时候看：提交前 + 提交后都会看到
听红框 = 系统已经发现风险 · 看蓝框 = 系统建议你勾选 gh-ost
经验 2: 错误优先级 (mixed_ddl > cross_db > pk_conflict)
实战经验：先报最严重的错（mixed_ddl 最严重，会让 SQL 全部丢失）
修法：先解决第一个红框，再解决第二个，按优先级顺序改
经验 3: 大表不勾 gh-ost = 锁表 5-30 分钟
阈值：100MB 或 10 万行
修法：勾 gh-ost（如果忘了勾，系统弹 alert + 自动勾上）
误判处理：小表误勾 gh-ost 也行，多花 30 秒，不会锁表
经验 4: 工单 SQL 越多越危险
修前：8 条 SQL 工单 7/8 失败（CREATE 全部丢失，wf#4841）
修后：v1 强制拆单，CREATE TABLE 跟 ALTER 分开提交
经验 5: 历史库不要手动改
修法：Archery 自动同步镜像工单
实战教训：手动改容易漏，Archery 自动不会漏
