v0.3.0-beta 2026-08-06 下午 commit 2c5a0b7 已发布（134 dev）
gh-ost 真跑阶段。完整 8 件交付，134 dev 真实演练 5 次全部 cut-over 成功。最关键的能力：业务表加列不再锁表。
  • 真启 gh-ost 子进程：runner.start_ghost_process Popen + nohup + systemd-run 临时 unit
  • stdout 解析器：parser.parse_ghost_log 兼容 gh-ost 1.1.10 输出（Time: 11s(total) / Done migrating）
  • 状态机自动推进：3s 轮询 + 外层 try/except 兜底（避免 daemon thread 异常静默死掉）
  • admin 三个 action：cancel / retry / rollback（含 rolled_back 终态）
  • 钉钉群通知：notify_terminal 终态发 webhook（best-effort，DINGTALK_NOTIFY_WEBHOOK 未配时自动 skip）
  • 暂停阈值：_maybe_pause_resume 查 MySQL Threads_running，超阈值 SIGSTOP
  • 影子表 7 天 cron：python manage.py cleanup_ghost_tables [--days N] [--dry-run]
  • 演练结果：accesscard_black_detail 加 beta_v2/v3_col + accesscard_account 加 beta_v4/v5_col，5 次 cut-over 全部成功，影子表无残留

风险与阻塞

Risks & Blockers
110 PROD MySQL 5.7.44 升级 8.0
当前 110 prod 用 5.7.44 + Django features.py patch (5, 7) 临时兼容。5.7 已 EOL，升级需独立项目评估（语法兼容性、字符集、复制拓扑等），不能跟在 v0.3.0 一起做。
134 dev archery instance user/password 是历史 mirage 加密密文
数据库里存的 user 是 'pn-OvgZNQs-v8A0VEmL_AA==' 这种 base64 密文，加密时的 K1 跟当前 SECRET_KEY K2 不匹配 → instance.get_username_password() 返回密文本身。临时方案：CUSTOM_GH_OST_PRECHECK_* 4 个 env 变量走 dbops 凭据直连。生产端需 DBA 重新保存 instance 触发 mirage 重新加密。
钉钉 OA 完整链路卡在用户操作上
v0.2.1（OA 模板）→ v0.2.2（隧道 + 回调加密）→ v0.2.3（对账）三步全部需要用户去钉钉开放平台操作。我这边技术实现已就绪（callback handler + 幂等 + 重试），但需要用户提供 process_code 和回调密钥才能继续推进。
110 PROD 钉钉通知 webhook 未配
gh-ost 真跑成功后 110 prod 应该发钉钉群通知，但 DINGTALK_NOTIFY_WEBHOOK 还没配。通知代码已写好（best-effort），等 webhook URL 后自动生效。
