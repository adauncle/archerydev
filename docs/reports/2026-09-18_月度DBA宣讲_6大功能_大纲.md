## ① 字段 diff 弹窗（功能 1，9/11 实战）

**Slide 标题**：「改一个列，Archery 告诉你会动哪些列」

**痛点（一句话）**：
> 业务方提交 `ALTER TABLE ... DROP INDEX`，Inception 只说"语法 OK"，没说"丢了哪个索引"。

**实战真实 case（git log + 演练脚本）**：

| commit | 实战 bug | 真实业务方工单 |
|---|---|---|
| 4b2d19c DBA-bug-1 | DROP INDEX 解析失败 | wf#4791 实战 |
| 7bd988b DBA-bug-2 | 反引号 schema 解析 + 主页面 banner | wf#4792 实战 |
| bac9e4f DBA-bug-3 | ADD/DROP INDEX 端点 ok=False 链路 bug | 字段 diff 大表 alert 丢失 |
| fd7c831 DBA-bug-3 hotfix | Django 跨行 {# #} 注释 JS SyntaxError | 弹窗 500 报错 |
| e22d874 DBA-bug-8 | 字段 diff 弹窗识别重复索引 | 业务方 add index idx_owner_name 实战 |
| 6ed3a77 DBA-bug-8 | regex bug fix - ADD INDEX name 后无空格 | 业务方实测触发 |

**修法（真实技术栈）**：
- 6 类 DDL regex 全覆盖（ALTER TABLE / DROP INDEX / ADD INDEX / MODIFY / ADD / DROP COLUMN）
- regex 一致性对齐：跟 `column_diff.py` / `sync_trigger.py` / `views.py:272` 三处统一格式
- 前端 escapeHtml() 防 XSS（DBA-bug-3 hotfix 实战教训）
- 9/16 DBA-bug-8 增加：information_schema.statistics 比对索引名（解决"新增 idx_owner_name 索引重复"误报）

**演练 case 数（真实）**：
- 9/11 DBA-bug-1 实战演练：`scripts/_dba_bug1_drill_134.py`
- 9/16 DBA-bug-8 单元 + 端到端

**业务价值（开发听得懂）**：
> 业务方提交工单，**弹窗自动告诉你改了什么**——不用等 DBA 人工审。

## ③ 历史库同步（功能 3，D35-DdlSync + DDL-Sync-Bug-A ⭐）

**Slide 标题**：「改了主库忘改历史库？Archery 自动帮你同步」

**痛点（一句话）**：
> 改了主库忘改历史库 → 3 个月后查历史库发现表结构对不上。

**真实实战 case（git log）**：

| **fe77c14** | **9/17 16:45** | **DDL-Sync-Bug-A 多 ALTER 工单 + 混合黑/白名单（wf#4841 形态）**|

**DBA-bug-5a 实战案例**：
- 业务方写 `ALTER TABLE \`hly_usercenter\`.\`accesscard_xxx\``
- sync_trigger.py regex 漏识别反引号 schema → 黑名单 miss → 镜像工单误生成
- 9/12 实战 1 天内修完

**DDL-Sync-Bug-A 新功能（9/17 新上线）**：

**业务背景**：业务方工单含多条 ALTER 时（如 wf#4841：4 CREATE + 4 ALTER），每条 ALTER 独立判定白/黑名单
- **修复前 Bug**：`_extract_table_name` 只返第一个 ALTER
  - blacklist 模式：第一个表在黑名单 → 整个工单不触发（其他白名单表也丢同步）
  - whitelist 模式：第一个表不在白名单 → 整个工单不触发
- 即使触发镜像工单，`ddl_text = sql_content` 全文不过滤

**修复后**：
- `_extract_all_alters()` 返 `list[{db, table, full}]`
- 每个 ALTER 独立判定白/黑名单
- skipped → `DdlSyncHistory(sync_status='skipped')`（DBA 排查）
- kept → 拼新 sql_content 创建镜像工单（只含 kept 的 ALTER）

**实战真实数据**：
- e2e PASS（134 dev 镜像工单 #10003 / 110 prod 镜像工单 #4859）
- wf#4841 形态验证

**DBA-bug-7 三表联动验证**：
- commit 7aa9fb4 + wf#4827-#4830 实战验证
- 三表：`wf.status` + `audit.current_status` + `DdlSyncHistory.sync_status`

**业务价值**：
> 业务方不用管历史库，**Archery 自动同步**（每条 ALTER 独立判定）。

## ④ 提交工单限制单库（功能 4，W3 9/16 新上线）

**Slide 标题**：「一个工单只能改一个库——跨库直接拒绝」

**痛点（一句话）**：
> 业务方 select A 库，SQL 写 B 库的表——Inception 不判定是不是 select 的库。

**真实业务方工单（wf#4821，9/16 实战）**：
```
use 'hly_accesscard'
ALTER TABLE accesscard_vehicle_change ADD COLUMN ocr_travel_vehicletype VARCHAR(150) DEFAULT NULL COMMENT '...'
ALTER TABLE hly_usercenter.accesscard_user_vehicle_change ADD COLUMN ocr_travel_vehicletype varchar(150) DEFAULT NULL COMMENT '...'
```
- 业务方 select `hly_accesscard`，但 ID 3 那条 SQL 改 `hly_usercenter.accesscard_user_vehicle_change`（跨库）
- Inception pass（语法 OK），Archery 上游完全没拦截

**修法（commit c65c93e + fda887c）**：
- 新建 `sql/utils/cross_db_check.py`（250 行，6 类 DDL/DML regex）
- 调研结论：Archery 上游 + inception/goinception **都没有跨库语义检测**，必二次开发
- 实战 bug fix（9/16 12:18，commit fda887c）：业务方多行无 `;`，regex `^\s*` 改 `\b`，finditer 全局扫描
- 前端 UX：红框 alert 在 inception-result 上面 + 按钮 disabled + 改文案"请先修复跨库/PK 冲突"

**演练 case 数（真实）**：
- 134 dev 单元测试 **16/16 PASS**（含 Case P wf#4821 多行无 `;` 实战回归）
- 134 dev 端到端 **11/11 PASS**
- 110 prod 跨库 **6/6 PASS**（含 wf#4821 K case 主验证）
- 业务方实测 **PASS**（9/16 12:50 阿达叔叔反馈，**显式写同库库名允许，跨库不允许**）

**业务价值**：
> 业务方提交前就**知道自己改错了库**。

## ⑤ 插入主键冲突检测（功能 5，W3 9/16 新上线）

**Slide 标题**：「INSERT 重复 PK？提交时就告诉你」

**痛点（一句话）**：
> 业务方 INSERT 15 条其中 6 条 PK 跟前面重复——Inception **不查 DB 现有 PK 值**。

**真实业务方工单（wf#4834，9/16 实战）**：
- 业务方 INSERT id 302-311 共 15 条（`INSERT INTO 'hly_datacenter_mod'.'output_fee_config'`）
- 实际执行到第 10 条才发现 `Duplicate entry '306' for key 'output_fee_config.PRIMARY'`
- 浪费 14 条 approve 工单流

**修法（commit c65c93e）**：
- 新建 `sql/utils/pk_conflict_check.py`（470 行）
- 直接 PyMySQL 连 DB 查 `information_schema.statistics` 拿 PK 列
- IN 列表限制 **1000** + LIMIT N（避免 SQL IN 太大）
- 实战踩坑 3 个：漏 `,` 切分 + 整行当 PK 值 + 漏负数（try/except int/float 统一处理）

**演练 case 数（真实）**：
- 134 dev 单元测试 **3/3 PASS**
- 134 dev 端到端 **4/4 PASS**
- 110 prod PK **4/4 PASS**
- 业务方实测 **PASS**（9/16 12:50）

**业务价值**：
> 提交时挡住，**业务方改 SQL 后再提交**——不用等执行报错返工。

## ⑥ v1 混合 DDL 禁止 + DBA-bug-10 CREATE INDEX 兼容（功能 6，**9/17 新上线** ⭐）

**Slide 标题**：「混合 DDL 禁止 + CREATE INDEX 等价 ALTER — 0 误报 0 漏报」

### 子功能 A — v1 混合 DDL 禁止提交

**痛点（一句话）**：
> 业务方工单含 CREATE + ALTER 混合时，旧提醒模式无效（业务方无视 banner 继续提交，导致 **7/8 失败**）。

**实战真实工单 wf#4841（9/16 实战，9/17 闭环）**：
- 业务方工单含 4 CREATE + 4 ALTER（accesscard_licensefront_info / vehicle_info_verify / accesscard_vehicle_review / accesscard_opendcardapply）
- 旧版提醒模式（v0.4.5 gh-ost）：前端加 banner 但只对 gh-ost 工单生效，业务方可以无视继续提交
- 工单显示"成功"但实际 **7/8 失败**（CREATE 全部丢失）

**拍板（9/17 13:06 阿达叔叔）**：从"提醒"升级"禁止"模式
- 9/17 09:30 备忘 commit `62b3cf2`
- 9/17 13:50 实现 commit `18e2ae3`

**修法（前后端双层防护）**：
- 前端：检测回调加 `mixed_ddl` 红框 alert + 阻止提交按钮 + 改文案"请先拆分工单 (ALTER 与 CREATE 不能混合)"
- 后端：`WorkflowContentSerializer.create()` 第一步 raise ValidationError（即使前端绕过 disable 按钮）
- 错误优先级：mixed_ddl > cross_db > pk_conflict
- 实战新发现：SQL 解析复用 `_detect_non_alter` 的 split + skip comments + first word token 思路（不写复杂 regex）

**演练 case 数（真实）**：
- 134 dev + 110 prod 双向 **8/8 PASS**（含 wf#4841 实战 4 CREATE + 4 ALTER）
- 后端兜底演练：POST mixed DDL → `status: 400 + error "工单含混合 DDL..."` ✅

### 子功能 B — DBA-bug-10 CREATE INDEX 等价 ALTER（5 文件统一修复）

**痛点（一句话）**：
> 业务方用 `CREATE INDEX ... ON 170万行表`，绕过所有 ALTER 检测（大表 alert / gh-ost / 字段 diff / 镜像工单）。

**实战真实工单 wf#4849（9/17 实战，9/17 闭环）**：
```sql
use `hly_accesscard`;
CREATE TABLE `consumetally_disputeorder_operation_log` (
  `id` bigint NOT NULL COMMENT '主键ID',
  PRIMARY KEY (`id`)
) COMMENT='争议数据操作日志表';
CREATE INDEX test USING BTREE ON hly_accesscard.accesscard_channel_task (req_url);
```
第 3 条 `CREATE INDEX ... ON accesscard_channel_task` 操作 170 万行 / 865 MB 表
- DBA 审核时**完全看不到大表 alert**（CREATE INDEX 绕过 ALTER 检测）
- 业务方走到"立即执行"路径要锁表 5-10 分钟

**根因**：`CREATE INDEX` 在 MySQL 等价 `ALTER TABLE ADD INDEX`，但代码只识别 `ALTER TABLE` 关键字

**修法（5 文件统一识别）**：
- `sql/views.py`：`_parse_first_alter` / `_parse_all_alters` / `_detect_non_alter` / `_check_mixed_ddl`
- `sql/extensions/ddl_gh_ost/views.py`：`_FIRST_CREATE_INDEX_RE` + `_parse_all_statements` CREATE INDEX 路径
- `sql/extensions/ddl_sync/services/sync_trigger.py`：`_CREATE_INDEX_PATTERN` + `_extract_all_alters`
- `sql/templates/sqlsubmit.html`：fetchColumnDiff 触发条件兼容 CREATE INDEX
- `sql/extensions/ddl_gh_ost/services/column_diff.py`（9/17 17:55 补漏）：`column_diff_full` + `_diff_single_table` 兼容 CREATE INDEX

**实战真实数据**：
- 演练 10/10 case PASS（双 regex / 实战 wf#4841 + wf#4849）
- 110 prod 大表演练 PASS（rows=1707167, size_mb=865.4）
- 9/17 17:52 阿达叔叔截图 110 prod 提交页 → 弹大表 alert ✅（commit `2884b69` 补漏）

**业务价值**：
> 业务方不管用 ALTER 还是 CREATE INDEX 语法，**DBA 都能看到大表风险**（前-事阻断 vs 后-事拦截双管齐下）。
