## ① 字段 diff 弹窗（你提交 SQL 前会看到什么）

### 实战场景

你是开发，写完一段 SQL 准备提交：
```sql
ALTER TABLE hly_accesscard.accesscard_licensefront_info 
ADD COLUMN owner_name VARCHAR(64) DEFAULT NULL COMMENT '车主姓名';
```

### 触发条件
- SQL 含 `ALTER TABLE` 或 `CREATE INDEX`
- 不区分含字段 / 索引 / 表名修改

### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | 进入 **SQL 提交页** (`/submitsq/`) | 选实例 + 选库名 | 加载编辑器 |
| 2 | 编辑器 | 写你的 SQL | 实时语法高亮 |
| 3 | 点 **🔴 SQL检测** 按钮 | 触发检测 | 自动调 4 个端点：cross_db / pk_conflict / column_diff / gh_ost_precheck |
| 4 | 等待 1-2 秒 | — | 检测结果表 + 字段 diff 弹窗 + 大表 alert |
| 5 | 查看弹窗 | 看 before/after + 大表告警 | 弹窗里有列/索引变更 + rows/size_mb |

### 你应该看的反馈

```
[弹窗 1] 🔍 字段 diff
  ┌─────────────────────────────────┐
  │ owner_name  VARCHAR(64)  [+]新增  │  ← 绿色
  └─────────────────────────────────┘

[弹窗 2] ⚠ 大表 DDL（如触发）
  accesscard_licensefront_info
  扫描行数：1707167 / 阈值 100000
  大小：865.4 MB / 阈值 100 MB
  [✓] 启用 gh-ost 无锁变更 ← 系统自动勾
```

### 真实案例
- **wf#4791**（9/11）：业务方提交 `DROP INDEX`，弹窗显示"丢失索引 idx_xxx"，业务方提前加回
- **wf#4849**（9/17）：CREATE INDEX ON 170万行表 → 大表 alert 弹 + 字段 diff 弹
- **演练**：10/10 case PASS（含双 regex / 反引号 schema / USING BTREE / 不带 USING）

## ② 大表无锁变更 + v0 智能模式（怎么勾 gh-ost + 选模式）

### 实战场景

你改的表是 170 万行 / 865 MB（accesscard_channel_task），你不知道该不该勾 gh-ost。

### 触发条件
- 表 ≥ **100 MB** 或 ≥ **10 万行**（任一即可）

### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 选实例 + 库名 + 写 SQL | 编辑器加载 |
| 2 | 点 **🔴 SQL检测** | 触发检测 | 弹大表 alert 红框（含 rows + size_mb）|
| 3 | 看 alert | 确认表是大表 | 系统**自动**勾选 `☑ 启用 gh-ost 无锁变更` checkbox |
| 4 | 勾选后下拉框出现 | 选 gh-ost 模式 | 3 个选项：smart（默认）/ all_ghost / all_native |
| 5 | 默认选 **smart** | 推荐 90% 场景 | 多 ALTER 大小表混合自动分流 |
| 6 | 点 **🟢 SQL提交** | 提交工单 | 按钮变灰提示 loading → 提交成功 |

### gh-ost 模式怎么选

| 模式 | 适用 | 推荐度 | 你应该选 |
|------|------|--------|---------|
| **smart**（智能）| 单工单多 ALTER 大小表混合（90%）| ⭐⭐⭐ | **默认选这个** |
| **all_ghost** | 强制全表走 gh-ost（运维场景）| ⭐ | DBA 单独说才用 |
| **all_native** | 强制全表走原生（小表 / DBA 已评估）| ⭐⭐ | 不要乱用 |

### 真实案例
- **wf#4841**（9/16）：4 CREATE + 4 ALTER 大小表混合 → smart 模式自动分流，演练 7/7 PASS
- **110 prod 大表演练**：accesscard_dynamicaccountinfo (154 GB, hly_accesscard 库)
- **5A 拍板**：9/16 21:42 阿达叔叔同意

## ③ 历史库自动同步 + 多 ALTER 黑/白名单（你什么都不用做）

### 实战场景

你改了主库字段：
```sql
ALTER TABLE hly_accesscard.accesscard_xxx ADD COLUMN col int;
```

担心 3 个月后查历史库字段不存在。

### 触发条件
- 主库工单 `status = workflow_review_pass`（PASSED）
- 你配的库对（业务库 → 历史库）`enabled=True`

### 操作步骤（开发侧）

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 写主库 SQL + 提交 | 工单流转到审批 |
| 2 | 审批流程 | DBA 审批 | 工单 PASSED |
| 3 | **什么都不用做** | — | Archery 自动创建 `[镜像] xxx` 历史库工单 |
| 4 | 等历史库同步 | — | DBA 审批历史库镜像工单 + 执行 |

### 业务方视角

- ✅ 你什么都不用做（Archery 自动同步）
- ❌ 不要去历史库手动 ALTER（容易漏，Archery 不会漏）

### 多 ALTER 工单（DDL-Sync-Bug-A 修后）

**修前**：黑白名单只判定第一张表，其他表被丢同步
**修后**：每条 ALTER 独立判定

| 你的 ALTER | 白名单 | 黑名单 |
|-----------|--------|--------|
| accesscard_consumetally | ✅ 镜像工单含此 | skipped (DBA 看 history) |
| accesscard_black_detail | skipped | ✅ 镜像工单含此 |

### 真实案例
- **wf#4841 形态**：8 条 SQL 混合 → 黑白名单分别处理
- **110 prod 实战**：镜像工单 #4859（修后）
- **DDL-Sync-Bug-A e2e PASS**：134 dev 镜像工单 #10003

## ④ 限制单库（怎么避免跨库拦截）

### 实战场景

你写了 SQL 但没意识到混了两个库：
```sql
use 'hly_accesscard';
ALTER TABLE accesscard_vehicle_change ADD COLUMN col1 int;
ALTER TABLE hly_usercenter.accesscard_user_vehicle_change ADD COLUMN col2 int;  ← 跨库！
```

### 触发条件
- SQL 涉及多个 schema（库）
- 当前选的"库名" ≠ SQL 里 ALTER 的 schema

### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 顶部下拉选**实例** + **库名**（如 hly_accesscard）| 加载编辑器 |
| 2 | 编辑器 | 写你的 SQL | 实时高亮 |
| 3 | 点 **🔴 SQL检测** | 触发检测 | 跨库检测会扫所有 SQL 行涉及的库 |
| 4 | 弹红框 | 看错误文案 | "SQL 涉及库 ['hly_usercenter'] 跟您选的库 hly_accesscard 不一致" |
| 5 | 点 **🟢 SQL提交** | 按钮变灰 | 文案变 "请先修复跨库"，按钮不可点 |
| 6 | **修对 SQL** | 改 SQL 让所有 ALTER 都在同一个库 | 按钮自动恢复 "提交" 字样 |
| 7 | 再点 SQL提交 | 提交 | 成功 |

### 你应该知道的边界
- ✅ 显式写同库库名允许（如 `hly_accesscard.t1` ← 你选了 hly_accesscard）
- ❌ 跨库不允许（即使语法对，跨库就 reject）
- ⚠️ 特殊跨库需求 → 走 DBA 人工审批工单兜底

### 真实案例
- **wf#4821**（9/16 业务方实测）：2 张表的混合 → 弹红框 + 按钮变灰
- **演练 16/16 PASS**（含多行无 `;` 实战回归）+ **11/11 端到端** + **6/6 110 prod**

## ⑤ PK 冲突检测（怎么避免 INSERT 主键重复）

### 实战场景

你准备批量 INSERT：
```sql
INSERT INTO 'hly_datacenter_mod'.'output_fee_config' (id, name) VALUES
  (302, 'fee_a'),
  (303, 'fee_b'),
  (304, 'fee_c'),
  ...
  (306, 'fee_d'),  ← 实际 DB 里已存在 306！
  ...
```

### 触发条件
- SQL 含 INSERT（含 VALUES 子句）
- 表有主键（PRIMARY KEY）

### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 选实例 + 库名 + 表所在库 | 加载编辑器 |
| 2 | 编辑器 | 写 INSERT SQL | 实时高亮 |
| 3 | 点 **🔴 SQL检测** | 触发检测 | 调 `pk_conflict_check` 端点，查 `information_schema.statistics` |
| 4 | 弹红框 | 看错误 | "PK 值 [306, 307, 308, 309] 在 output_fee_config 表中已存在" |
| 5 | 点 **🟢 SQL提交** | 按钮变灰 | 文案变 "请先修复 PK 冲突"，按钮不可点 |
| 6 | **改对 PK** | 让 PK 自增或跳过已存在的 | 按钮自动恢复 "提交" 字样 |
| 7 | 再点 SQL提交 | 提交 | 成功 |

### 边界
- ✅ 单次 INSERT 支持最多 **1000** 个 PK 值
- ✅ 多个 INSERT 一起检测
- ❌ 不要碰运气让执行到第 N 条才发现 Duplicate entry

### 真实案例
- **wf#4834**（9/16 业务方实测）：id 302-311 共 15 条，其中 4 条重复 → 弹红框 + 列出具体 PK 值
- **演练 3/3 PASS** + **4/4 端到端** + **4/4 110 prod**

## ⑥ v1 + DBA-bug-10（混合 DDL 拆单 + CREATE INDEX 等价 ALTER）

### 子功能 A — v1 混合 DDL 禁止

**实战场景**：你工单含 8 条 SQL 混 CREATE + ALTER：
```sql
ALTER TABLE hly_accesscard.accesscard_licensefront_info ADD INDEX idx_owner_name (owner_name);
ALTER TABLE hly_accesscard.vehicle_info_verify ADD COLUMN col int;
CREATE TABLE hly_accesscard.accesscard_opendcardapply (id int);  ← CREATE 混进来！
CREATE INDEX test_idx ON hly_accesscard.accesscard_opendcardapply (col);
... 8 条 SQL
```

#### 触发条件
- 工单含 `CREATE TABLE / VIEW / DATABASE` 跟 `ALTER TABLE` 混合
- **`CREATE INDEX` 不算混合**（它就是 ALTER ADD INDEX 的语法糖）

#### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 写混合 SQL | 实时高亮 |
| 2 | 点 **🔴 SQL检测** | 触发检测 | 弹红框："请先拆分工单 (ALTER 与 CREATE 不能混合)" |
| 3 | 点 **🟢 SQL提交** | 按钮变灰 | 文案变 "请先拆分工单" |
| 4 | **拆分 SQL** | 拆成 2 个工单：① ALTER 4 条 ② CREATE 4 条 | — |
| 5 | 分别提交 | 提交 2 个工单 | 全部成功 |

#### 双层防护
- 前端：按钮 disable + 红框 alert
- 后端：`WorkflowContentSerializer.create()` raise ValidationError（即使前端绕过也兜底）

#### 真实案例
- **wf#4841**（9/16 业务方实测）：4 CREATE + 4 ALTER → 修前 7/8 失败 → 修后拆单全成功
- **演练 8/8 PASS**（134 dev + 110 prod 双向）

### 子功能 B — DBA-bug-10 CREATE INDEX 等价 ALTER

**实战场景**：你用 CREATE INDEX 给大表加索引：
```sql
CREATE INDEX test USING BTREE ON hly_accesscard.accesscard_channel_task (req_url);
```

#### 触发条件
- SQL 含 `CREATE [UNIQUE|FULLTEXT|SPATIAL] INDEX`
- 表 ≥ 100MB 或 ≥ 10万行

#### 操作步骤

| 步骤 | 在哪操作 | 做什么 | 系统反馈 |
|------|---------|--------|---------|
| 1 | SQL 提交页 | 写 CREATE INDEX SQL | 实时高亮 |
| 2 | 点 **🔴 SQL检测** | 触发检测 | 弹大表 alert（170万行/865MB）+ 字段 diff |
| 3 | 看 alert | 确认是大表 | 系统**自动**勾选 `☑ 启用 gh-ost 无锁变更` |
| 4 | 提交 | 走 gh-ost 切流 | 0-30 秒切流完成 |

#### 真实案例
- **wf#4849**（9/17 业务方实测）：CREATE INDEX on 170万行表 → 大表 alert 弹 + 自动勾 gh-ost
- **110 prod 演练**：rows=1707167, size_mb=865.4
- **演练 10/10 case PASS**（含双 regex / 反引号 schema / USING BTREE / 不带 USING）
