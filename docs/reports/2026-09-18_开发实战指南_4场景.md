## 场景 A：我写完 SQL 该提交了，会不会影响生产？

**场景**：你是开发，写完一段 `ALTER TABLE` 或 `CREATE INDEX`，准备提交。

### A.1 提交那一刻会发生什么？

**系统自动弹 3 个东西**（你什么都不用做）：

```
[1] 字段 diff 弹窗 → 告诉你这次 DDL 影响哪些列/索引
[2] 大表检测 → 你的表 ≥ 100MB 或 ≥ 10 万行就弹红色 alert
[3] gh-ost 提示 → 大表自动勾选 gh-ost 无锁变更
```

### A.2 实战案例：wf#4849（9/17 业务方实战）

**业务方写的 SQL**：
```sql
CREATE INDEX test USING BTREE ON hly_accesscard.accesscard_channel_task (req_url);
```

**Archery 弹了什么**（修后）：
```
⚠️ 检测到 accesscard_channel_task 是大表 DDL
   · 扫描行数：1707167
   · 大小：865.4 MB
   · 阈值：100000 行 / 100 MB
   
[启用 gh-ost 无锁变更]  ← 系统帮你勾上了
```

**业务方做了什么**：
- 看到红框 → 知道是大表
- 系统自动勾 gh-ost → 不锁表
- 直接提交 → 切流 0-30 秒

**你作为开发应该做的**：
- ✅ 看到红框不要慌，系统已经帮你勾好 gh-ost
- ✅ 确认 SQL 是 ALTER 还是 CREATE INDEX（修后两种都识别）
- ❌ 不要在 wf 里偷偷去掉 gh-ost 勾选（去掉就锁表）

### A.3 真实数据（演练 + 实战）

- 演练 10/10 case PASS（双 regex / 实战 wf#4841 + wf#4849）
- 110 prod 大表演练：accesscard_channel_task rows=1707167, size_mb=865.4
- 9/17 17:52 阿达叔叔截图 110 prod 提交页 → 大表 alert + gh-ost 选项自动出现 ✅

## 场景 B：我提交了，为什么弹红框？

**场景**：你提交工单后，前端变红，按钮变灰，弹了一堆错误。

### B.1 优先级（先看哪个错）

**错误优先级**：`mixed_ddl` > `cross_db` > `pk_conflict`

```
mixed_ddl 红框 = CREATE + ALTER 混了 → 必须拆单
cross_db 红框  = 跨库了 → 必须改对库
pk_conflict 红框 = INSERT 主键重复 → 必须改 PK
```

**优先级逻辑**：先报最严重的（mixed_ddl 最严重，因为它会让 SQL 全部丢失）

### B.2 mixed_ddl 红框 — 工单里有 CREATE + ALTER

**实战案例**：wf#4841（9/16 业务方实战，9/17 闭环）

**业务方写的 SQL**：
```sql
ALTER TABLE hly_accesscard.accesscard_licensefront_info ADD INDEX idx_owner_name (owner_name);
ALTER TABLE hly_accesscard.vehicle_info_verify ADD COLUMN col int;
CREATE TABLE hly_accesscard.accesscard_opendcardapply (id int);
CREATE INDEX test_idx ON hly_accesscard.accesscard_opendcardapply (col);
... 8 条 SQL
```

**旧版（修前）**：
- 弹 banner 提醒："工单含 4 CREATE + 4 ALTER，请拆单"
- 业务方无视 banner → 提交 ✅（按钮还能点）
- 工单显示"成功" → 实际 **7/8 失败**（CREATE 全部丢失，只 1 条 ALTER 走通）

**新版（修后）**：
- 弹红框："请先拆分工单 (ALTER 与 CREATE 不能混合)"
- 提交按钮**变灰**，文案："请先拆分工单"
- 即使前端绕过 → 后端 `WorkflowContentSerializer.create()` 兜底 reject
- 拆单后再提交 → 全部成功

**你作为开发应该做的**：
- ✅ CREATE TABLE / VIEW / DATABASE 跟 ALTER TABLE 分开提交
- ✅ CREATE INDEX **不**算混合（它就是 ALTER ADD INDEX 的语法糖）
- ❌ 不要混着提，否则就算前端没拦住，后端也拦

### B.3 cross_db 红框 — 跨库了

**实战案例**：wf#4821（9/16 业务方实测）

**业务方写的 SQL**：
```sql
use 'hly_accesscard';
ALTER TABLE accesscard_vehicle_change ADD COLUMN ocr_travel_vehicletype ...;
ALTER TABLE hly_usercenter.accesscard_user_vehicle_change ADD COLUMN ocr_travel_vehicletype ...;  ← 跨库！
```

**Archery 弹**：
```
🛡️ SQL 涉及库 ['hly_usercenter'] 跟您选的库 hly_accesscard 不一致
[请先修复跨库] ← 按钮变灰
```

**你作为开发应该做的**：
- ✅ 选对库（页面顶部"库名"下拉）
- ✅ 显式写同库库名允许，跨库不允许
- ❌ 不要想着"反正语法对，让 DBA 帮我改库"

### B.4 pk_conflict 红框 — INSERT 主键重复

**实战案例**：wf#4834（9/16 业务方实测）

**业务方写的 SQL**：
```sql
INSERT INTO 'hly_datacenter_mod'.'output_fee_config' (id, ...) VALUES (302, ...);
INSERT (304, ...);
...
INSERT (306, ...); ← 已存在！
```

**Archery 弹**：
```
🔑 PK 值 [306, 307, 308, 309] 在 output_fee_config 表中已存在
[请先修复 PK 冲突] ← 按钮变灰
```

**你作为开发应该做的**：
- ✅ 改对 PK 值（让 PK 自增或跳过已存在的）
- ✅ 1000 条 INSERT 没问题（PK 检测支持最多 1000）
- ❌ 不要碰运气让执行到第 N 条才发现 Duplicate entry

### B.5 真实数据（演练 + 业务方实测）

- mixed_ddl 演练 8/8 PASS（134 dev + 110 prod 双向）
- W3 跨库演练 16/16 + 11/11 + 6/6 PASS + 业务方实测 PASS（9/16 12:50）
- PK 演练 3/3 + 4/4 + 4/4 PASS + 业务方实测 PASS（9/16 12:50）

## 场景 C：我工单里有 8 条 SQL，大小表混合，怎么搞？

**场景**：你的工单含多张表（有的 1 万行，有的 1000 万行），你不知道每张表该用哪种变更方式。

### C.1 旧版（修前）

- 你必须**手动判断**每张表的大小
- 手动决定哪些走 gh-ost，哪些走原生 ALTER
- 一不小心大表走原生 → 锁表 5-30 分钟

### C.2 新版（v0 智能模式，修后）

**选项 `smart`（默认）**：
```
系统自动判断每张表的大小
├── < 100MB 且 < 10 万行 → 走原生 ALTER（不切流）
└── ≥ 100MB 或 ≥ 10 万行 → 走 gh-ost（无锁切流）
```

**业务方只需要**：选 `smart` 模式 → 什么都不用选 → 提交 → 等切流完成

### C.3 实战案例：wf#4841（9/16，9/17 闭环）

**业务方工单含 4 CREATE + 4 ALTER**：
```sql
ALTER TABLE accesscard_licensefront_info ADD INDEX idx_owner_name (owner_name);        -- 大表 (5M+ 行)
ALTER TABLE vehicle_info_verify ADD COLUMN col int;                                       -- 中表
ALTER TABLE accesscard_vehicle_review ADD INDEX idx_x (col);                              -- 大表
ALTER TABLE accesscard_opendcardapply ADD COLUMN col int;                                 -- 中表
```

**修后跑 v0 智能模式**：
- 4 大表 → 自动走 gh-ost（每个一个 task）
- 4 中表 → 自动走原生 ALTER
- 业务方**什么都不用选**

**110 prod 真实大表演练**：accesscard_dynamicaccountinfo (154 GB, hly_accesscard 库)

### C.4 三种模式可选

| 模式 | 适用 | 推荐度 |
|------|------|--------|
| **smart**（智能）| 单工单多 ALTER 大小表混合（90% 场景）| ⭐⭐⭐ 默认 |
| **all_ghost** | 全表都强制走 gh-ost（极少用，运维场景）| ⭐ |
| **all_native** | 全表都走原生 ALTER（小表，或 DBA 已评估过）| ⭐⭐ |

### C.5 真实数据（演练 + 实战）

- v0 演练 7/7 case PASS（含 wf#4841 实战 4 ALTER 形态）
- 110 prod 实战大表演练：accesscard_dynamicaccountinfo (154 GB)
- 134 dev 演练用 archery_dev.accesscard_black_detail (134 MB)
- 5A 拍板：9/16 21:42 阿达叔叔同意

## 场景 D：我改了主库字段，历史库怎么办？

**场景**：你改了主库 `hly_accesscard.accesscard_xxx` 加了字段，但历史库 `hly_accesscard_history.accesscard_xxx` 没改。3 个月后查历史库发现字段不存在。

### D.1 旧版（修前）

- 业务方手动改两边 → 漏改 → 3 个月后报错
- 业务方不手动改 → DBA 排查 1 小时才发现

### D.2 新版（修后）

**主库 DDL 上线后**：
1. Archery 自动检查：你配的库对（业务库 → 历史库）有没有镜像工单需要开
2. 自动创建历史库镜像工单（工单名：`[镜像] {你的工单名}`）
4. DBA 审批镜像工单 + 执行
5. 历史库同步完成

**你作为开发**：
- ✅ 什么都不用做（Archery 自动同步）
- ❌ 不要去历史库手动 ALTER（避免两边不一致）

### D.3 多 ALTER 工单（DDL-Sync-Bug-A 修后）

**修前**：多 ALTER 工单黑白名单只判定第一张表，其他表被丢同步

**修后**：每条 ALTER 独立判定
- blacklist 模式：在黑名单的 ALTER → `DdlSyncHistory(skipped)`，业务方+ DBA 看 history 知道漏同步
- whitelist 模式：在白名单的 ALTER → 创建镜像工单
- 混合：黑白名单分别处理，镜像工单只含白名单的 ALTER

### D.4 实战案例

**wf#4841 形态（9/17 e2e 演练）**：
- 业务方工单 4 CREATE + 4 ALTER，黑白名单混合
- 修后：黑名单 2 条 ALTER 写 `DdlSyncHistory(skipped)`
- 白名单 2 条 ALTER 拼成镜像工单（只含白名单的 ALTER，不带黑名单）
- 110 prod 镜像工单 #4859 实战验证

**业务方完全无感**：主库改完，3 个月后查历史库字段都在 ✅

### D.5 真实数据（演练 + 实战）

- DDL-Sync-Bug-A e2e PASS（134 dev 镜像工单 #10003 / 110 prod 镜像工单 #4859）
- DBA-bug-5a 实战（9/12）修反引号 schema
- DBA-bug-7 三表联动验证（wf.status + audit.current_status + DdlSyncHistory.sync_status）

## 🔥 关键经验总结（让开发少走弯路）

### 经验 1: 字段 diff 弹窗 = 你提交前最后一道防线
**触发条件**：含 ALTER TABLE / CREATE INDEX 的 SQL
**什么时候看**：提交前 + 提交后都会看到
**听红框 = 系统已经发现风险**，听蓝框 = 系统建议你勾选 gh-ost

### 经验 2: 错误优先级 (mixed_ddl > cross_db > pk_conflict)
**实战经验**：先报最严重的错（mixed_ddl 最严重）
**修法**：先解决第一个红框，再解决第二个，按优先级顺序改

### 经验 3: 大表不勾 gh-ost = 锁表 5-30 分钟
**阈值**：100MB 或 10 万行
**修法**：勾 gh-ost（如果忘了勾，系统弹 alert + 自动勾上）
**误判处理**：小表误勾 gh-ost 也行，多花 30 秒，不会锁表

### 经验 4: 工单 SQL 越多越危险
**修前**：8 条 SQL 工单 7/8 失败（CREATE 全部丢失）
**修后**：v1 强制拆单，CREATE TABLE 跟 ALTER 分开提交

### 经验 5: 历史库不要手动改
**修法**：Archery 自动同步镜像工单
**实战教训**：手动改容易漏，Archery 自动不会漏
