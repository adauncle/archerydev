04演示 1 — 字段 diff 检测

Use case · 事故 A 字符集飘字段

故事

业务 RD 提了一条 ALTER TABLE t MODIFY c VARCHAR(50) DEFAULT '' COMMENT '备注', 想给 c 加 comment, 但漏写 CHARSET utf8mb4。 运维上线后, 表 8 个字段中 3 个是 latin1 (跟原 schema 不一致), 新写入数据乱码。

解法

在 SQL 提交页 + 工单详情页 都加"字段 diff" 按钮, 调 MySQL 解析 alter 前后的 SHOW CREATE TABLE, 字段级 diff。

实战数据 (演练)

=== 字段 diff 检测结果 ===

字段 c (VARCHAR(50)):
  - 类型:    VARCHAR(50) → VARCHAR(50)        ✓ 不变
  - 字符集:  utf8mb4 → latin1                ⚠️ 飘字段
  - 默认值:  '' → ''                          ✓ 不变
  - Comment: '' → '备注'                      ✓ 变 (符合预期)

字段 d (VARCHAR(100)):
  - 字符集:  utf8mb4 → latin1                ⚠️ 飘字段
  - 字符集:  utf8mb4 → latin1                ⚠️ 飘字段
共 2 个字段字符集飘了! 是否继续?

业务价值: 字符集飘字段那种"漏写 CHARSET 导致全表飘字段"的事故, 上线前业务 RD 提交时就能看到警示, 不上线就改。 不需要 DBA 复盘, 也不依赖业务 RD 自觉看 MySQL 文档。

一键复制修正 SQL

字段 diff 弹窗底部有个"复制完整修正 SQL" 按钮, 一键复制带 CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci 的完整 DDL, 业务 RD 贴回去就行, 不用手写。

05演示 2 — gh-ost 大表 DDL

Use case · 事故 B 大表漏勾 + 事故 D 碎片回收

故事

业务 RD 提了一条 ALTER TABLE access_log ADD COLUMN region VARCHAR(20), 表 30w 行。 漏勾 gh-ost, 走原路径 ALTER, 锁表 4 分钟, 业务侧 RT 飙到 30s+, 工单被打回。

解法 (3 层防护)

第 1 层 · 提交页

业务 RD 提交时勾"启用 gh-ost", 系统自动检测表大小, 大表强制推荐勾选。

第 2 层 · 详情页 (大表防呆)

表 ≥ 10w 行 / 100MB, 详情页显示红色 alert, 3 个按钮: 启用 gh-ost / 立即执行 (双层 confirm) / 终止工单。

第 3 层 · DBA 兜底

DBA 看到工单后, 也能直接勾 gh-ost 启用 (DBA perm), 不需要业务 RD 重提。

5 关预检 (gh-ost 启用后)

详情页点"启用 gh-ost" 后, 系统跑 5 关预检, 全 PASS 才允许执行:

关检查项阈值为什么
1 binlog_format = ROW 必须 ROW gh-ost 监听 binlog, STATEMENT/MIXED 看不到
2 磁盘剩余空间 ≥ 1.2 × 表大小 gh-ost 创建 ghost 影子表, 需要 ~原表大小
3 账号权限 ALL PRIVILEGES gh-ost 需要 ALTER/CREATE/DROP/INDEX/INSERT/SELECT
4 ALTER SQL 合法 支持 ADD/DROP/MODIFY, 禁 RENAME TO / TRUNCATE gh-ost 工具本身限制
5 表类型 InnoDB + 非分区 + 非临时 gh-ost 1.1.x 不支持 MyISAM / 分区表 / FEDERATED

进度面板 (gh-ost 执行中)

通过预检后, 系统起 gh-ost 子进程, 详情页显示进度面板, polling 3s 刷新 (不是 SSE/WebSocket, 简单可控):

事故 D · 碎片回收 (DBA 专用)

DBA 想给 accesscard_black_detail 回收碎片, 传统 ALTER TABLE ENGINE=InnoDB 会锁表 30+ 分钟。 gh-ost 走触发空 alter: ALTER TABLE t ENGINE=InnoDB, ROW_FORMAT=原值, DEFAULT CHARSET=原值 COLLATE=原值, 0 锁表 物理页重写 + DATA_FREE 归零。

事故 D 拍板 3 决策: ① alter 用 ENGINE=InnoDB, ROW_FORMAT=<原值>, DEFAULT CHARACTER SET=<原值> COLLATE=<原值> 3 层防护 ② rebuilt_charset / rebuilt_row_format / rebuilt_at 字段记录 ③ 任务列表显示 "ALTER 子句" 列, 让 DBA 一眼看出改了什么

06演示 3 — 智能回滚

Use case · 事故 C 切流超时

故事

业务侧灰度发布, 新表上线后切流到 30%, 报 column not found 错误, 切回 100% 老表。 原因: DDL 改了字段, 但没有回滚 SQL, 想撤就全乱。只能临时禁用代码 + 紧急回滚代码 + 紧急回滚 DDL, 3 步操作, 整个流程 1 小时+。

解法 (A+B 方案)

A 方案 · 智能逆向 (主力, 5 种 DDL)

解析 ALTER, 自动生成反向 SQL:

原 SQL:    ALTER TABLE t ADD COLUMN c INT
回滚 SQL:  ALTER TABLE t DROP COLUMN c

原 SQL:    ALTER TABLE t MODIFY COLUMN c BIGINT
回滚 SQL:  ALTER TABLE t MODIFY COLUMN c INT

原 SQL:    ALTER TABLE t DROP COLUMN c
回滚 SQL:  ALTER TABLE t ADD COLUMN c INT   (需要备份字段定义)

原 SQL:    ALTER TABLE t RENAME TO t2
回滚 SQL:  ALTER TABLE t2 RENAME TO t

原 SQL:    ALTER TABLE t ADD INDEX idx (c)
回滚 SQL:  ALTER TABLE t DROP INDEX idx
B 方案 · 兜底 (不支持时)

解析不出时返 warnings, 列出不支持的子句:

⚠️ unsupported_keywords = [
  "FOREIGN KEY",   # 外键约束, 暂不支持
  "FULLTEXT",      # 全文索引, gh-ost 也不支持
  "RENAME TO"      # gh-ost 限制
]

提示: 请人工生成回滚 SQL, 或联系 DBA
提示: 建议提前备份 DDL / 表结构

⚠️ 字段 DROP 时需要原字段定义
提示: 在原 DDL 前先备份字段定义:
  SHOW CREATE TABLE t;
  -- 复制原字段定义

位置

智能回滚按钮在 工单详情页 + gh-ost 任务详情: - 详情页: "已申请 gh-ost 无锁变更 · 等待审批通过" 旁, "智能回滚" 按钮 - 进度面板: "查看回滚 SQL" 按钮 - 任务列表 (DBA 视角): "回滚" 操作端点

业务价值: 切流超时那种"切流切不回" 的事故, 现在 DBA 1 分钟内拿到回滚 SQL, 直接执行, 整个事故从 1 小时 → 5 分钟。

07gh-ost 任务管理 (DBA 视角)

DBA Tooling · 运维入口

DBA 需求

本专题立项时拍板: DBA 视角"运维工具台", 不是单个人的任务管理。需求 3 个: 1. 看全量任务 (自己提的 rebuild + 业务 RD 提的 ghost) 2. 操作端点 perm 守卫 (cancel / retry / rollback / start 只能 DBA 用) 3. 任务状态联动 (SqlWorkflow 终止时, DdlGhostTask 也跟着清理)

3 决策拍板

决策方案原因
权限 用 Django admin 自动注册的 4 perm (view/add/change/delete), 0 DB 改动 跟 8/12 gh-ost 任务管理 / 字段 diff 一致, 不引入新 perm 模型
可见性 DBA 看全量, 业务 RD 只看自己 (group filter) 业务 RD 不应该看到别人的 DDL 工单
操作端点 perm helper 返 JsonResponse({ok: False, error: "..."}, status=403), 不能 raise PermissionDenied AJAX 端点 raise 会冒到 Django middleware, 返 403 HTML 错误页, alert 弹 HTML 源码 (立项时实战踩坑)

状态机三件套

5 个终态: success / failed / cancelled / panic / completed, 加上僵尸 socket 双层防御:

  1. poller 5s 检查: 任务状态切 terminal, 自动清理 /tmp/gh-ost.*.sock
  2. 新任务启动前: rm -f /tmp/gh-ost.*.sock 防止残留 socket 报错

088/24 一天 3 个 bug 修复

Bug Fix · 实战案例

8/24 一天修了 3 个 Archery 上游 bug + 固化 1 个教训 SOP。 W3 推 110 之前这段"补漏洞"很值, 推上去的版本更稳。

Bug 1 · 审批流覆盖 (ConfigurableAuditor 修法)

症状: 业务 RD 提 SQL_REVIEW 工单, 详情页审批流显示 3 级 (14,15,3), 但 config 配的 2 级 (14,3)。

根因: 8/11 加的 ConfigurableAuditor.generate_audit_setting 命中 policy 时, 用 flow.audit_auth_groups="14,15,3" 覆盖上游 WorkflowAuditSetting="14,3"。业务 RD 困惑"我配了不生效"。

修法 (commit a41c4d0): 命中 policy 时直接走 super 用 Archery 上游 WorkflowAuditSetting (source of truth), driver 路由仍生效。

教训: Archery 上游 config/ 页面配的审批流是 source of truth, 改了立即生效 — 二次开发不能覆盖。

Bug 2 · gh-ost precheck 过度限制

症状: 业务 RD 提 ALTER TABLE t DROP COLUMN c 勾选 gh-ost, 预检 FAIL "检测到禁用操作 DROP"。

根因: 8/06 v0.3.0-alpha 加 FORBIDDEN_ALTER_OPERATIONS = ("RENAME", "DROP", "TRUNCATE"), 凭印象写没查 gh-ost 官方文档。实际 gh-ost 1.1.x 明确支持 DROP COLUMN (Limitations 列表里没 DROP)。

修法 (commit 9d66064): FORBIDDEN_ALTER_OPERATIONS 移除 "DROP", 只保留 RENAME / TRUNCATE。顺手修 "TRUNCATE;" 边界 case 漏报。

教训: 二次开发涉及第三方工具能力 (gh-ost / SOAR / sqladvisor), 必查官方 docs/limitations, 不要从代码脑补。8/18 教训 (业务配置查审批日志) + 8/24 教训 (工具能力查 docs) 组成跨项目可复用对子。

Bug 3 · cancel 已审核工单抛 "审批权限组不存在"

症状: 工单 #88 审核通过后, DBA 点"终止流程" 按钮, 报错"当前审批权限组不存在, 请联系管理员检查并清洗错误数据"。

根因: Archery 上游 cancel 流程把"有 sql_review perm 但非 engineer" 的人映射到 REJECT, can_operate REJECT 路径无条件查 Group.objects.get(id=current_audit)。已审核工单 current_audit = "-1", 必抛 DoesNotExist。

修法 (commit eaf9853): can_operate REJECT 路径加判断 if current_audit == "-1": return True。已审核工单跳过 Group 检查 (权限已在 can_cancel + has_perm 验证过)。

098/24 教训 + 标准化 SOP

Standardization · 跨项目可复用

关键教训: gunicorn HUP 不重载 Python 代码

8/24 改 ConfigurableAuditor 后, HUP master 38114 → 4s 后新 worker 50625 fork 出来, 实际没加载新代码。 提工单 #85: 提交页显示 2 级 (走 Audit.settings() 老接口), 详情页显示 3 级 (走 ConfigurableAuditor.generate_audit_setting 老代码, 写表被覆盖)。

根因: gunicorn fork 模式 master 启动时把 Python module import 进 sys.modules, worker fork 时继承 master 的内存映像。 HUP master 只重启 worker 进程, 不会重新 import。HUP 只对 settings.py / os.environ 改动有效, 改业务代码看不到。
