功能 ①

① 字段 diff 弹窗 — 改表前看影响

场景：你写完一段 ALTER 准备提交，想知道会影响哪些列
ALTER TABLE hly_accesscard.accesscard_licensefront_info ADD COLUMN owner_name VARCHAR(64) DEFAULT NULL COMMENT '车主姓名';
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页
/submitsq/		 顶部下拉选 实例 + 库名（如 hly_accesscard） 编辑器加载
2 SQL 编辑器 写你的 ALTER/CREATE INDEX SQL 实时语法高亮
3 点 🔴 SQL检测 按钮 触发检测（自动调 4 个端点：cross_db / pk_conflict / column_diff / gh_ost_precheck） 等待 1-2 秒
4 查看反馈 字段 diff 弹窗 + 检测结果表 + 大表 alert 列/索引变更可视化
📋 你应该看到的弹窗
🔍 字段 diff：owner_name VARCHAR(64) [+] 新增（绿色）
⚠️ 大表 DDL：accesscard_licensefront_info 行 1707167 / 大小 865.4 MB（超阈值）
✓ 启用 gh-ost 无锁变更 ← 系统帮你自动勾上

功能 ②

② 大表无锁 + v0 智能 — 怎么勾 gh-ost + 选模式

场景：你的表 170 万行 / 865 MB，系统自动帮你勾 gh-ost
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页 选实例 + 库名 + 写 SQL 编辑器加载
2 点 🔴 SQL检测 触发检测 弹大表 alert 红框（含 rows + size_mb）
3 看 alert 确认表是大表（≥ 100MB 或 ≥ 10 万行） 系统自动勾选 ☑ 启用 gh-ost 无锁变更 checkbox
4 勾选后下拉框出现 选 gh-ost 模式（smart / all_ghost / all_native） 默认 smart（推荐 90% 场景）
5 点 🟢 SQL提交 提交工单 按钮变灰提示 loading → 切流 0-30 秒
smart
⭐ 默认选
大小表混合自动分流（大表 gh-ost + 小表原生 ALTER）
推荐 90% 场景
all_ghost
运维场景
强制全表都走 gh-ost（运维 / DBA 评估后）
all_native
DBA 评估
强制全表都走原生 ALTER（DBA 已评估）
04 / 9
功能 ③

③ 历史库自动同步 — 你什么都不用做

场景：你改了主库字段，担心 3 个月后历史库字段对不上
ALTER TABLE hly_accesscard.accesscard_xxx ADD COLUMN col int;
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页 写主库 DDL + 点 🟢 SQL提交 工单流转到审批
2 审批流 DBA 审批 → 工单 workflow_review_pass PASSED 状态
3 ⏸️ 开发侧什么都不用做 Archery 自动创建 [镜像] xxx 历史库工单
4 （观察进度） 等历史库同步完成 DBA 审批历史库镜像工单 + 执行
✅ 多 ALTER 工单（DDL-Sync-Bug-A 修后）
修前：黑白名单只判定第一张表，其他表被丢同步
修后：每条 ALTER 独立判定 · 黑名单 DdlSyncHistory(skipped) · 白名单 拼成镜像工单
05 / 9
功能 ④

④ 限制单库 — 跨库怎么拦截

场景：你 SQL 写了两个库的表，没意识到是跨库
use 'hly_accesscard'; ALTER TABLE accesscard_vehicle_change ADD COLUMN col1 int; ALTER TABLE hly_usercenter.accesscard_user_vehicle_change ADD COLUMN col2 int; ← 跨库！
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页顶部 下拉选 实例 + 库名（如 hly_accesscard） 加载编辑器
2 编辑器 写你的 SQL 实时高亮
3 点 🔴 SQL检测 触发检测 跨库检测扫所有 SQL 行的 schema
4 看红框 看错误文案 "SQL 涉及库 ['hly_usercenter'] 跟您选的库 hly_accesscard 不一致"
5 点 🟢 SQL提交 按钮变灰 文案变 "请先修复跨库"，按钮不可点
6 改对 SQL 把所有 ALTER 改到同一个库 按钮自动恢复 "提交" 字样
06 / 9
功能 ⑤

⑤ PK 冲突检测 — INSERT 重复 PK 怎么拦截

场景：你准备批量 INSERT，没意识到 PK 跟表里现有数据重复
INSERT INTO 'hly_datacenter_mod'.'output_fee_config' (id, name) VALUES (302, 'fee_a'), (303, 'fee_b'), ... (306, 'fee_d'), ← DB 里 306 已存在！
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页 选实例 + 库名 + 表所在库 加载编辑器
2 编辑器 写 INSERT SQL 实时高亮
3 点 🔴 SQL检测 触发检测 调 pk_conflict_check 端点，查 information_schema.statistics
4 看红框 看错误 "PK 值 [306, 307, 308, 309] 在 output_fee_config 表中已存在"
5 点 🟢 SQL提交 按钮变灰 文案变 "请先修复 PK 冲突"
6 改对 PK 让 PK 自增或跳过已存在的 按钮自动恢复 "提交"
📋 边界
✅ 单次 INSERT 支持最多 1000 个 PK 值 · ✅ 多个 INSERT 一起检测
❌ 不要碰运气让执行到第 N 条才发现 Duplicate entry
07 / 9
功能 ⑥ A

⑥ v1 混合 DDL 禁止提交 — 8 条 SQL 混 CREATE + ALTER

场景：你工单含 CREATE + ALTER 混合（修前 7/8 失败，修后拆单全成功）
ALTER TABLE hly_accesscard.accesscard_licensefront_info ADD INDEX idx_owner_name (owner_name); ALTER TABLE hly_accesscard.vehicle_info_verify ADD COLUMN col int; CREATE TABLE hly_accesscard.accesscard_opendcardapply (id int); ← CREATE 混进来！ CREATE INDEX test_idx ON hly_accesscard.accesscard_opendcardapply (col); ...
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页 写混合 SQL 实时高亮
2 点 🔴 SQL检测 触发检测 检测结果表第 2 行显示 warning
3 看红框 看错误 "请先拆分工单 (ALTER 与 CREATE 不能混合)"
4 点 🟢 SQL提交 按钮变灰 文案变 "请先拆分工单"
5 拆分 SQL 拆成 2 个工单：① ALTER 4 条 ② CREATE 4 条 —
6 分别提交 提交 2 个工单 全部成功
双层防护
前端：按钮 disable + 红框 alert
后端：WorkflowContentSerializer.create() raise ValidationError（即使前端绕过也兜底）

功能 ⑥ B

⑥ DBA-bug-10 CREATE INDEX 等价 ALTER

场景：你用 CREATE INDEX 给大表加索引（修前绕过所有检测，修后弹大表 alert）
CREATE INDEX test USING BTREE ON hly_accesscard.accesscard_channel_task (req_url);
步骤 在哪操作 做什么 系统反馈
1 SQL 提交页 写 CREATE INDEX ... ON tbl (col) 实时高亮
2 点 🔴 SQL检测 触发检测 检测识别 CREATE INDEX 等价 ALTER
3 看红框 看大表 alert accesscard_channel_task 行 1707167 / 大小 865.4 MB
4 确认 gh-ost 查看 gh-ost 自动勾选状态 系统自动勾选 ☑ 启用 gh-ost 无锁变更
5 点 🟢 SQL提交 提交 走 gh-ost 切流 0-30 秒
📋 实战案例（wf#4849）
业务方 CREATE INDEX on accesscard_channel_task (170 万行 / 865 MB) → 大表 alert 弹 + 自动勾 gh-ost → 切流完成
演练 10/10 case PASS（双 regex / 反引号 schema / USING BTREE / 不带 USING）
