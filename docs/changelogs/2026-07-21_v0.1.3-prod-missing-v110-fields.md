# 2026-07-21 · v0.1.3-prod 修 v1.10.0 漏跑的字段

## 症状

用户 Navicat 导入 v1.10.0 数据后，登录页能进，但 `/sqlworkflow/` 报 500：

```
django.db.utils.OperationalError: (1054, "Unknown column 'sql_instance.is_ssl' in 'field list'")
```

## 根因

**v0.1.0 部署时漏跑了 `src/init_sql/v1.10.0.sql`**（`deploy_prod.sh` 的升级 SQL loop 里没有 `10.0` 这一项，跳过去了）。

`v1.10.0.sql` 引入了两个 schema 改动：
1. `sql_instance` 加 `is_ssl tinyint(1)` 字段（SSL 支持）
2. `instance_account` 加 `db_name varchar(128)` 字段（MongoDB 多库支持）
3. 重建 `instance_account` 唯一索引为 4 字段联合（instance_id, user, host, db_name）

`v1.10.0.sql` 之后的上游 SQL（v1.11/12/13/14/15）都没引用 `is_ssl` 或 `db_name`，所以单独跳 v1.10.0 不会暴露问题 —— **直到 v1.10.0 源库的数据导入后**，Django ORM 查 `is_ssl` 才报缺字段。

## 修复

`scripts/deploy/fix_v110.sql`（2500 字节）：

1. `SET @col_exists = ... PREPARE/EXECUTE` 判断列是否存在，**幂等**（重复跑安全）
2. 加 `is_ssl` 字段
3. 加 `db_name` 字段
4. 重建 4 字段联合唯一索引（这一步当前被外键拦住，**不影响功能** —— 老 3 字段 unique index 还在用）

## 修复后状态

- `sql_instance.is_ssl`: tinyint(1) DEFAULT 0 ✓
- `instance_account.db_name`: varchar(128) NOT NULL DEFAULT '' ✓
- `/sqlworkflow/`: HTTP 302（不再是 500）✓
- 不需要重启 gunicorn（MySQL schema 变更 ORM 自动感知）

## deploy_prod.sh 修复

`scripts/deploy/systemd/deploy_prod.sh` 升级 SQL loop 增加 `v1.10.0` 和 `v1.15.0`（之前漏了）：

```diff
- for f in .../v1.{1.0,2.0,3.0,3.2,...,9.0,10.0,12.0,13.0}.sql; do
+ for f in .../v1.{1.0,2.0,3.0,3.2,...,9.0,10.0,12.0,13.0,15.0}.sql; do
```

下次部署 prod 会跑 v1.10.0.sql（schema 跟 v1.14.0 完全对齐），不再漏字段。

## 教训

1. **漏 1 个升级 SQL 不会立即报错**，要等用到该 SQL 引入的字段才会爆
2. **deploy loop 应该**：
   - 完整列出 `src/init_sql/` 下的所有文件（用 `ls v1.*.sql`），不要手写
   - 跑完后对比 `git show HEAD~1 --stat | grep init_sql` 确认所有文件都跑过
3. **跨版本数据迁移前**：
   - 必跑 schema 升级 SQL（不是可选）
   - 必保留源库 SECRET_KEY（v1.10.0 用了 mirage 加密，没有源 key 就解不开密文）
   - 跑完 `DESCRIBE` 表结构 + 查 `INFORMATION_SCHEMA.columns` 跟目标 model 字段 diff
4. **Navicat 全量导入**只能导数据，**不会改 schema**（因为目标表已存在），所以源库有的字段目标库必须有，否则查询报错
