# 8/28 DDL 跨库同步 v0.5.0-r3 重大决策变更: 走当前配置的流程 (8/28 16:15)

## 背景

- 8/28 14:00 v0.5.0-r2 一键配机制 (commit `26937cb`) 落地
- 8/28 14:55 + 15:30 + 15:45 HTML 表总数/库名对齐真实数据 (commit `586fffc` / `22d7066` / `db03cba`) 落地

- 8/28 16:15 DBA 拍板 (朴素方案): "**生成历史库工单, 按照当前配置的流程走就行, 我调整成什么流程, 就怎么走. 和正常工单一样**"

## 决策

**自动生成的历史库镜像工单, 走当前 Archery 配置的流程, 跟正常历史库工单一样**。

- DBA 在 Archery 后台改"prod core for 历史库" 组的流程 (单级 / 双级 / 加 leader), 镜像工单自动同步
- v0.5.0 代码**不写**"由谁审" / "走几级", 完全用 Archery 现成的 `workflow_audit_setting.audit_auth_groups` 配置
- **0 额外代码**, 复用现有 `SqlWorkflow` + `audit_setting` 机制

## 跟 8/21 拍板对比 (重大变更)

| 维度 | 8/21 拍板 (作废) | 8/28 拍板 (采用) |
|------|----------------|----------------|
| 审批人 | 同业务库 DDL 审批人 (3 级) | **按当前 Archery 配置 (DBA 配的) 走** |

8/21 拍板时**没想清楚**, 8/28 拍板是"想清楚了" 的版本。

## 实施原则 (3 个)

1. **自动生成的镜像工单跟正常工单一样** — 不在 v0.5.0 代码里写"由谁审" / "走几级", 完全用 Archery 现成的 `workflow_audit_setting.audit_auth_groups` 配置. DBA 后台改什么, 镜像工单就怎么走.
2. **业务库 DDL 必须审过 (`current_status=1 PASSED`) 才触发镜像工单** — 实施: 镜像工单创建 trigger 加 `if source_workflow.current_status != 1: return None`. 这是底线, 业务库 DDL 没审过不联动.
3. **业务 RD 实时通知 (钉钉 OA)** — 业务库 DDL 触发镜像工单时, 钉钉通知业务 RD: "你的 DDL `#12345` 触发了历史库工单 `#12346` 状态: 审核中/执行中/已完成". 让业务 RD 知道"我的 DDL 触发了历史库 DDL", 不丢控.

## 安全护栏 (3 个必加)

虽然走当前流程, 但要加 3 个安全护栏防风险:

1. **业务库 DDL 必审过 trigger** — 见实施原则第 2 条
2. **历史库执行前预演 + 异常 rollback** — 跟 v0.4.5 智能回滚 联动 (8/13 拍板, 已落地). 复用 8/13 拍的 rollback 端点 (`services.db._get_creds` + DROP TABLE IF EXISTS 兜底)
3. **异常通知 DBA + 业务 RD** — 跟 v0.2.0 钉钉 OA 联动, 异常立刻钉钉通知 DBA + 业务 RD, 不依赖业务 RD 自己查工单状态

## 教训 (跨项目可复用, 2 条新增)

### 1. **"和正常工单一样" 是更优雅的设计原则**
用户原话: "**生成历史库工单, 按照当前配置的流程走就行, 我调整成什么流程, 就怎么走. 和正常工单一样**". 这个原则的好处:
- **0 额外代码** — 复用现有 `SqlWorkflow` + `audit_setting` 机制
- **0 重复配置** — DBA 改一次配置, 手动提的工单 + 自动生成的工单 同步生效
- **避免"配置漂移"** — 不需要为"自动生成" 单独搞一套审批逻辑, 不会出现"DBA 改了 prod core for 历史库组的流程, 镜像工单没跟进" 的坑
**下次设计"自动生成的工单" 场景: 必演"复用现有配置" 原则, 不为自动生成单独搞配置/代码**. 8/21 拍板时**没意识到这个原则**, 写了"同业务库审批人" 模糊描述, 8/28 DBA 拍板时才明确.

### 2. **"DBA 朴素的方案" 往往是最优方案**
DBA 8/28 16:15 拍板 "和正常工单一样" 这 13 个字, 比我之前给的"5 个理由 + 3 个护栏" 详细方案 还要精准. DBA 拍板时是从"使用方怎么想" 出发 (8/28 r2 教训), 不是从"技术上能怎么做" 出发.
- 我之前给的方案: "走历史库流程 (DBA 审 + DBA 执行)" — 具体, 但限制了 DBA 改配置的灵活性 (如果 DBA 以后想加"DBA 组长" 审, v0.5.0 代码就 hardcode 错了)
- DBA 拍板: "走当前配置的流程" — 抽象, 但给 DBA 留了配置空间
**下次给 DBA 拍板方案: 抽象原则 > 具体规则**. 拍板原则让 DBA 自己定具体配置, 拍板规则我 hardcode 到代码里反而限制 DBA.
