01概览: 两个功能解决两件事

gh-ost 解决"大表 DDL 锁表", 字段 diff 解决"DDL 改错字段"。两个功能互不依赖, 但放在 Archery 同一个 extension (ddl_gh_ost), 业务用户一次提交就能同时享受两个保护。

🛡️

gh-ost 无锁 DDL

大表改 DDL 不锁表, 业务照常读写。gh-ost 工具建影子表 + binlog 同步, 平滑切流。

🔍

字段 diff 检测

提交 DDL 时自动对比新旧字段定义, 11 条规则检测风险 (字符集/类型/长度/索引/默认值)。

🔄

碎片回收 (gh-ost 触发空 alter)

DBA 兜底工具, 一键触发"空 alter" (ENGINE+ROW_FORMAT+CHARSET) 回收表碎片, 走 gh-ost 不锁表。

📋

DDL 智能回滚

DDL 失败自动回滚, ADD COLUMN → DROP, MODIFY → 改回原值, 不留半残状态。

03字段 diff 检测 (核心算法)

3.1 三个核心步骤

① 查当前列定义

information_schema.columns
拿到 type / charset / collation / nullable / default / comment / key

② 解析 ALTER 子句

正则匹配 MODIFY / CHANGE / ADD / DROP
解析新列定义结构化

③ 11 规则风险评估

逐字段对比 (old, new)
返 (risk_level, reason)

3.2 11 条风险规则详解

每条规则是独立函数, 返回 (risk_level, reason) 二元组。3 个等级: high / mid / low / none (无变化)。

规则函数触发条件风险等级典型案例
_assess_type_risk基础类型不兼容 / 长度缩短高 / 中 / 低VARCHAR(100) → VARCHAR(64) (中) / INT → BIGINT (低)
_assess_charset_risk字符集变化高utf8mb4 → utf8 (生产事故根因!)
_assess_collation_risk排序规则变化高utf8mb4_general_ci → utf8mb4_unicode_ci
_assess_nullable_risknullable ↔ NOT NULL中 / 低NULL → NOT NULL (中, 需要先填默认值)
_assess_default_risk默认值变化中DEFAULT 0 → DEFAULT NULL (新行行为变)
_assess_column_key_riskPRIMARY KEY 变化高PRI → 空 (主键丢失, 影响查询计划)
_assess_extra_riskauto_increment / on_update 等中丢失 auto_increment (新增需显式给值)
comment 变化COMMENT 'old' → 'new'低无影响

3.3 字符集丢失的根因 + 防护

🚨

8/13 生产事故: 业务 RD 写 ALTER TABLE t MODIFY col VARCHAR(64), 以为字符集不变, 实际 Archery 解析时新字段的 CHARACTER_SET_NAME 字段为空 (DDL 没带), 跟原表的 utf8mb4 比对判为"字符集变化", 实际执行时 MySQL 8.0 把字段字符集设为 utf8mb3 (默认), 跟其它 utf8mb4 字段 JOIN 时索引失效。

防护机制:

  1. 字段 diff 检测"字符集变化" 标红高风险
  2. "📋 复制补全 SQL" 按钮生成"强制带原 CHARSET + COLLATE" 的 DDL
  3. 前端 modal 强制 DBA 看到字符集风险, 不允许"忽略"

3.4 边界场景 (开发要知道)

场景处理
多 ALTER 子句 (逗号分隔)正则拆 4 种操作, 逐个评估
CHARSET 在表级不在字段级用 "(table default)" 标记, 仍标高风险
复合类型如 ENUM / SET简化按 VARCHAR 评估, 可能误报
函数 DEFAULT (CURRENT_TIMESTAMP)识别为函数式, 单独处理
信息架构查不到 (权限不足)返空 dict, 前端"无法检测"提示

4.4 poller.py 关键设计 (跟 8/13 踩坑)

⚠

踩坑 (8/13): 业务 RD 反馈 "gh-ost 进程卡死, 进度不更新"。根因: poller 守护线程的 subprocess.Popen.stdout.readline() 在 gh-ost 切流阶段会阻塞 (没有新输出), 看门狗超时没生效。
修法: 用 selectors.DefaultSelector + 非阻塞读取 + 外层 30s 超时 + daemon 线程有 try/except 外层兜底。

4.5 切流机制 (3 种模式)

模式行为适用
--cut-over=default (推荐)gh-ost 自适应, atomic 优先, 失败 fallback two-step大多数场景
--cut-over=atomic原子切流, 短暂锁表 (RENAME 原子操作)业务可以接受瞬时阻塞
--cut-over=two-step两步切流, 阻塞写操作更短对延迟敏感场景

4.6 zabbix socket 双层防御

防 zombie socket (gh-ost 进程死了但 socket 还在):

  1. Archery 端 task 状态每 3s 轮询, 超时切 failed
  2. gh-ost 进程启时 subprocess.Popen 设置 start_new_session=True, 进程独立组
  3. 业务 RD / DBA 点"取消"时, 先 terminate() 再 kill() 兜底
  4. 外层 try/except 捕获 gh-ost crash, 写 error_message 切 failed

06碎片回收 (3 决策详解)

6.1 问题: MySQL 5.7 OPTIMIZE TABLE 锁表

MySQL 5.7 走 OPTIMIZE TABLE = ALTER TABLE ... ENGINE=InnoDB, 但 5.7 不支持 ALGORITHM=INPLACE, LOCK=NONE, 走 COPY 锁表, 大表 (百万行) 锁几分钟, 业务感知强。

6.2 解法: 走 gh-ost 触发"空 alter"

gh-ost 复制 + 切流, 不锁表。但需要"触发整表物理页重写" 的 alter 子句 (空改不会触发)。

6.3 3 决策 (开发拍板)

决策 1: alter 子句 = ENGINE + ROW_FORMAT + DEFAULT CHARSET + COLLATE

3 层防护, 0 风险飘字段:

ALTER TABLE accesscard_black_detail
  ENGINE=InnoDB
  ROW_FORMAT=DYNAMIC
  DEFAULT CHARACTER SET=utf8mb4
  COLLATE=utf8mb4_general_ci;
否决方案 A: 改 COMMENT='archery-auto-rebuild-YYYYMMDD'
问题: 破坏表 COMMENT 业务描述, 数据治理出大问题
否决方案 B: 改 ROW_FORMAT=DYNAMIC 单独触发
问题: 某些 MySQL 版本 ROW_FORMAT 改跟自己一样可能 no-op, 不触发重写
决策 2: 记录 rebuilt_charset / rebuilt_row_format / rebuilt_at 字段

DBA 一眼看出"这次 rebuild 改了什么", 字段加在 DdlGhostTask 上:

rebuilt_charset     = "utf8mb4"          # 改后字符集
rebuilt_row_format  = "DYNAMIC"          # 改后 ROW_FORMAT
rebuilt_at          = "2026-08-13 10:00"  # rebuild 完成时间
决策 3: 任务列表页显示 "ALTER 子句" 列

DBA 一眼看到 rebuild 改了什么, 不需要查 task detail:

┌──────┬────────┬───────────┬────────────────────────────────┐
│ #ID  │ 库.表  │ 提交人    │ ALTER 子句 (truncated)         │
├──────┼────────┼───────────┼────────────────────────────────┤
│ #86  │ access │ DBA 手动  │ ENGINE=InnoDB ROW_FORMAT=...  │
└──────┴────────┴───────────┴────────────────────────────────┘

07DDL 智能回滚 (A+B 方案)

7.1 A 方案: 5 种 DDL 智能逆向

DDL 失败时, 自动从原始 schema 快照生成回滚 SQL:

原 DDL自动回滚能否自动
ADD COLUMN x VARCHAR(64)DROP COLUMN x✅ 智能逆向
MODIFY COLUMN x VARCHAR(100)MODIFY COLUMN x VARCHAR(50) (从快照读原值)✅ 智能逆向
CHANGE COLUMN x y VARCHAR(64)CHANGE COLUMN y x VARCHAR(64)✅ 智能逆向
DROP COLUMN xADD COLUMN x ... (从快照读)✅ 智能逆向
RENAME TABLE a TO bRENAME TABLE b TO a✅ 智能逆向

7.2 B 方案: 兜底 (不支持的 DDL)

遇到不常见 DDL, 返 warnings 不自动回滚, DBA 人工处理:

# sql/services/ghost_task_sync.py
def _reverse_single_op(op_text, snapshot):
    """单条 ALTER 操作智能逆向"""
    op_upper = op_text.upper().strip()

    # 优先检测 FOREIGN KEY / INDEX 等不支持逆向 (用 in 而非 startswith)
    unsupported_keywords_contains = ("FOREIGN KEY",)
    if any(kw in op_upper for kw unsupported_keywords_contains):
        return None, "FOREIGN KEY 不支持自动回滚, 需 DBA 人工处理"

    # 操作关键词 (用 startswith)
    unsupported_keywords_startswith = ("ADD INDEX", "DROP INDEX", "ADD PRIMARY KEY")
    if any(op_upper.startswith(kw) for kw unsupported_keywords_startswith):
        return None, "INDEX 变更不支持自动回滚"

    # 智能逆向 (5 种支持的操作)
    if op_upper.startswith("ADD "):
        return _reverse_add(op_text)
    if op_upper.startswith("MODIFY "):
        return _reverse_modify(op_text, snapshot)
    # ...
    return None, "未知 DDL 类型, 不支持自动回滚"

7.3 顺序踩坑 (8/13 教训)

🚨

8/13 教训: 一开始把 unsupported_keywords 用一个 tuple, 全部 in 判断。
问题: "ADD INDEX" in "ALTER TABLE t ADD INDEX idx_x (col)" 返 False (因为 ADD INDEX 是 substring), "DROP INDEX" in "ALTER TABLE t DROP INDEX idx_x" 返 True 但顺序错了会先匹配 "ADD " 走智能逆向逻辑。
修法: 拆 2 个 tuple — unsupported_keywords_contains (用 in, 优先检测 FOREIGN KEY 这种 substring) + unsupported_keywords_startswith (用 startswith, 检测操作关键词)。

08踩坑教训 (8 条)

开发要懂这些坑, 避免重蹈覆辙。每条都对应一个具体 commit / 决策。

🚨 教训 1: GoInception panic on MODIFY COLUMN

症状: 业务 RD 跑 gh-ost 任务, 报 Lost connection to MySQL server during query

根因: GoInception 1.x 在 ALTER TABLE ... MODIFY COLUMN 解析时, 触发 Go runtime panic (slice bounds out of range)

触发条件: 大表 + MODIFY + bigint → varchar (varchar→varchar / int→bigint / ADD/DROP/RENAME 不触发)

修法: 字段 diff 端点走 pymysql 直连, 不依赖 goinception; 8/13 临时 workaround systemctl restart goinception

长期修法: 升级 goinception 1.x → 最新版, 推 110 时同步升级

🚨 教训 2: 字符集丢失 (生产事故)

症状: 业务库加字段后, 跨表 JOIN 索引失效, 性能暴跌

根因: ALTER 没带 CHARACTER SET utf8mb4, MySQL 8.0 默认字符集变 utf8mb3, 跟其它 utf8mb4 字段 JOIN 时索引不可用

修法: 字段 diff 检测"字符集变化" 标红高风险 + "📋 复制补全 SQL" 按钮生成强制带原字符集的 DDL

🚨 教训 3: 业务 RD 不知道 gh-ost (DBA 兜底产品定位)

症状: 业务 RD 提大表 DDL, 直接执行, 锁表 30s, 业务感知

根因: 业务 RD 不知道 gh-ost 工具, Archery 没主动提示

修法: 大表 DDL 防呆 3 按钮 (启用 gh-ost / 立即执行 / 终止) + DBA 兜底机制 + 详情页大表 alert

⚠️ 教训 4: AJAX 端点 raise PermissionDenied 弹 HTML

症状: 业务 RD 点"取消任务", alert 弹一整页 HTML 源码

根因: 取消 / 重试 / 回滚 3 个端点 raise PermissionDenied, Django middleware 返 403 HTML 错误页, AJAX 拿到整页 HTML 源码

修法: helper 返 JsonResponse({"ok": False, "error": "..."}, status=403) 替代 raise

⚠️ 教训 5: drill 验证严谨度 (8/13 副标题提取)

症状: gh-ost 端到端演练时, 副标题断言失败 — 因为用了 re.DOTALL 跨行匹配, 把后面的内容也吃掉了

根因: 副标题在多行 HTML 里, 用 .* 跨行匹配会匹配太多

修法: 抓首个 <p class="gh-ost-sub">...</p> 用 (.*?) 非贪婪 + non-dotall 模式

⚠️ 教训 6: 业务配置 ID 必须看实际审批日志

症状: 用户报"134 审批流程是研发-研发组长-dba", 我误读成 13,14,3, 改了 fix_approval_flow_3level.py + init_fallback_flow.py, 实际正确配是 14,15,3 (研发组长→DBA组长→DBA)

根因: 从代码 / auth_group 表脑补 group ID 语义, 没看 Archery 实际审批日志

修法: 涉及 Archery 业务配置 (审批组 ID / 角色 / perm) 必须看 workflow_audit_setting + 实际审批日志 + admin 后台, 不要从代码脑补

⚠️ 教训 7: 业务定位文案修正

症状: 字段 diff 标题"(DBA 兜底)" 让业务 RD 困惑, 跳 admin 后台"权限组管理"链接误以为是普通功能

根因: 产品定位文案没考虑实际用户

修法: 字段 diff 标题去"(DBA 兜底)" / 弹窗去"权限组管理"链接 / 详情页大表 alert 保留"DBA 兜底启用 gh-ost" (业务 RD 需要知道)

⚠️ 教训 8: 默认权限最小化 (8/13 拍板)

症状: 业务 RD 默认能看到 gh-ost 任务管理菜单, 困惑

根因: 早期 perm 守卫太松, 业务 RD 默认有 view perm

修法: 业务 RD 默认不勾任何 gh-ost perm, 业务 RD 组长可勾 view (只能看, 不能改), DBA 勾全 4 个

09业务场景案例 (4 个真实)

宣讲时, 用这 4 个真实案例跟业务团队共鸣 — 都是 8 月份踩过的坑。

📌 案例 1: 业务 RD 提大表 DDL, 字段 diff 提示字符集丢失

背景: 业务 RD 8/13 提 ALTER TABLE accesscard_black_detail MODIFY COLUMN card_no VARCHAR(64) (大表, 120 万行)

Archery 检测: 字段 diff 显示"字符集变化: utf8mb4 → utf8, 跨表 JOIN 索引可能失效"

修法: 业务 RD 点"📋 复制补全 SQL", 生成 ALTER TABLE ... VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci

结果: 审批通过, 走 gh-ost 跑 3 分钟, 业务零感知, 索引没失效

教训: 字符集没带会跨表 JOIN 索引失效, 11 条规则重点防护

📌 案例 2: 业务 RD 漏勾 gh-ost, DBA 兜底

背景: 业务 RD 8/15 紧急修复上线, 提了 ALTER TABLE log_record ADD INDEX idx_xxx, 大表 80 万行, 没勾 gh-ost

DBA 收到工单: 详情页大表 alert 弹出"未启用 gh-ost"

DBA 操作: 点"🛠️ DBA 兜底启用 gh-ost", 工单自动改走 gh-ost

结果: 审批通过, gh-ost 跑 4 分钟, 业务零感知

教训: 紧急情况漏勾, DBA 兜底是最后一道防线

📌 案例 3: gh-ost 切流超时, 智能回滚兜底

背景: 业务 RD 8/19 业务高峰期提了 MODIFY COLUMN bigint → varchar (大表, 业务低峰期踩点失败)

gh-ost 切流超时: 一直有 DML 阻塞, 切流 30 分钟没成功

详情页提示: "切流超时, 失败, 触发智能回滚"

v0.4.5 智能回滚: 自动生成 MODIFY COLUMN col bigint 改回原值, 跑成功

结果: 业务表回到原状态, 不用 gh-ost 切流, 工单标 failed 但不留半残

教训: 选业务低峰期; 智能回滚 5 种 DDL 全覆盖, 不用 DBA 手动

📌 案例 4: DBA 兜底定期碎片回收

背景: 业务库 8/20 健康检查发现 accesscard_black_detail 碎片率 42% (DATA_FREE 38GB), MySQL 5.7 OPTIMIZE TABLE 锁表

DBA 决定: 用碎片回收, 走 gh-ost 不锁表

DBA 操作: 访问 /gh_ost/rebuild/list/ → 选 3 张表 → 点"一键回收"

触发空 alter: ENGINE=InnoDB ROW_FORMAT=DYNAMIC DEFAULT CHARACTER SET=utf8mb4 COLLATE=utf8mb4_general_ci

结果: gh-ost 异步跑 8 分钟, 碎片归零, 业务零感知

教训: ENGINE+ROW_FORMAT+CHARSET 3 层防护, 0 风险飘字段

10.2 现场答疑 (10 个常见问题)

Q1: 字段 diff 跟 SQL 审核有什么区别?
SQL 审核是"SQL 语法 + 业务规则" 检查 (走 goinception), 字段 diff 是"字段定义变更前后" 对比。两者互补不冲突, SQL 审核过了再走字段 diff。
Q2: 字段 diff 检测失败怎么办?
查 information_schema 没权限或网络不通, 返 "无法检测" 提示, 不阻塞工单提交。但强烈建议 DBA 检查凭据。
Q3: gh-ost 跟主从延迟有关系吗?
有, gh-ost 默认 --max-lag-millis=1500 阈值, 主从延迟超 1.5s 会暂停切流, 等延迟恢复再切。
Q4: gh-ost 跑一半挂了, 影子表会留下吗?
会。Archery 端任务状态切 failed, 影子表 (原表_gho / _ghc) 残留。Archery 端有清理脚本 (cleanup_ghost_tables management command), DBA 跑一下清掉。
Q5: gh-ost 切流期间业务会卡住多久?
atomic 模式 1-3 秒, two-step 模式几百毫秒。阻塞期间所有写操作排队, 业务感知但不丢数据。
Q6: 字段 diff 11 条规则够用吗?
覆盖 90% 生产事故根因 (字符集/类型/长度/索引/默认值)。其他罕见 DDL 走 warning, 不强制 block。
Q7: 业务 RD 漏勾 gh-ost 怎么办?
详情页大表 alert 弹出, DBA 点"🛠️ DBA 兜底启用 gh-ost" 按钮, 工单自动改走 gh-ost。这是最后一道防线, 业务 RD 不需要慌。
Q8: gh-ost 跟其他 DDL 工单互斥吗?
互斥。同一张表跑 gh-ost 时, 其他 DDL 工单 (包括 ALTER) 会被 DdlGhostTask 状态机锁住, 避免切流冲突。
Q9: 智能回滚会丢数据吗?
不会。ADD COLUMN 智能回滚是 DROP COLUMN, 没新增数据; MODIFY COLUMN 智能回滚是改回原值, 已变更的数据保留; 系统会检测"字段有非默认值" 时返 warnings 让 DBA 确认。
Q10: gh-ost 跟业务主从切换兼容吗?
兼容。gh-ost 跑期间主从切换, 影子表在原 master, 切流后 RENAME 原子操作在新 master。gh-ost 自动重连新 master, 不需要人工介入。

10.3 宣讲避坑 (3 个不要)

⚠

不要 1: 不要给业务 RD 讲架构细节 — 业务 RD 不关心 poller 怎么实现, 只关心"我能点哪个按钮"。架构细节放设计稿 (docs/designs/), 不放宣讲手册。

⚠

不要 2: 不要承诺"gh-ost 一定不锁表" — 切流期间 atomic 模式阻塞 1-3 秒, 写操作排队。诚实说"业务零感知" 而不是"零阻塞"。

⚠

不要 3: 不要演示未跑过的功能 — 4 个案例是 8 月真实跑过的, 拿来宣讲有底气。临时加的"未来会做"功能别演示, 容易被打脸。
