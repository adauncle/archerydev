01概览: 5 分钟搞懂 gh-ost + 字段 diff

这两个功能解决两件事: 大表 DDL 不锁表 (gh-ost) + 字段变更风险检测 (字段 diff)。一起用, 大表 DDL 变更就稳了。

🛡️

gh-ost 无锁 DDL

大表改 DDL 不用锁表, 业务照常读写。gh-ost 工具会建影子表 + binlog 同步, 平滑切换。

v0.3.0 无锁

🔍

字段 diff 检测

提交 DDL 时自动对比新旧字段定义, 11 条规则检测风险 (字符集/类型/长度/索引/默认值)。

v0.3.x 风险

DBA 兜底工具, 一键触发"空 alter" (ENGINE+ROW_FORMAT+CHARSET) 回收表碎片, 不用锁表。

02快速开始 (业务 RD)

5 分钟走一遍完整流程, 后面看细节。

1打开 SQL 提交页
侧边栏 → SQL 审核 → 提交工单
2选实例 + 库 + 写 DDL
在文本框里写你的 ALTER TABLE, 不用带 IF EXISTS, Archery 帮你处理。
3看字段 diff 自动检测结果
文本框下面会出"字段变更检测"面板, 显示变更前后对比 + 风险等级 (高/中/低)。看高风险, 字符集变化是最容易踩的坑。
4如果是大表, 勾选"启用 gh-ost"
大表 (行数 > 10 万 或 数据 > 100MB) 提交时会弹"大表 DDL 防呆"提示, 三个按钮: 启用 gh-ost / 立即执行 (锁表) / 终止工单。强烈建议选"启用 gh-ost"。
5提交工单 + 走审批
点"提交", 工单进入审批流 (DBA 会审)。审批通过后, 如果勾了 gh-ost, 会用 gh-ost 跑; 否则走普通 SQL 执行。
6看进度 / 失败处理
工单详情页有"gh-ost 进度"链接, 进去看实时进度 (复制了多少行 / 卡在哪一步 / 预计完成时间)。失败时点"取消"或"重试"。
💡

业务 RD 必看: 第 3 步字段 diff 检测是全自动的, 你不用主动调, 提交时自动跑。11 条规则覆盖 90% 生产事故根因 (字符集变化、类型缩短等)。

03业务 RD · 提工单时

3.1 字段 diff 自动检测

提交 ALTER TABLE 时, Archery 自动调字段 diff 端点, 显示变更前后对比:

archery.local/sqlsubmit/ · 字段变更检测
📋 字段变更检测 3 条风险
表: oa.accesscard_black_detail
原 DDL: ALTER TABLE accesscard_black_detail MODIFY COLUMN card_no VARCHAR(64);
🔴 高风险 (1) 字符集变化: utf8mb4 → utf8mb3, 跨表 JOIN 索引可能失效 (生产事故根因!)
🟡 中风险 (1) 类型缩短: VARCHAR(100) → VARCHAR(64), 已有数据可能截断
🟢 低风险 (1) COMMENT 变更: '老注释' → '新注释' (无影响)
💡 建议: 强制带 CHARSET utf8mb4 跟原表一致, 避免索引失效
📋 复制补全 SQL 🛠️ 启用 gh-ost

"复制补全 SQL" 按钮很关键 — 点了它会生成"强制带原字符集 + 原排序规则"的 DDL, 避免你忘了写字符集导致生产事故:

复制后: ALTER TABLE accesscard_black_detail MODIFY COLUMN ...
✓ 补全后: 
ALTER TABLE accesscard_black_detail MODIFY COLUMN card_no VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
↑ 注意: 自动补了 CHARSET 和 COLLATE 跟原表一致, 避免跨表 JOIN 索引失效

3.2 11 条字段 diff 风险规则 (速查)

规则风险等级典型场景应对
基础类型不兼容高VARCHAR → TEXT / INT → BIGINT数据格式/索引可能丢失, 改回
字符集变化高utf8mb4 → utf8 / 不带 CHARSET生产事故根因, 强制带原 CHARSET
排序规则变化高utf8mb4_general_ci → utf8mb4_unicode_ci排序/大小写敏感行为会变, DBA 确认
类型缩短中VARCHAR(100) → VARCHAR(64)已有数据可能截断, 查 max 值再改
类型变长低VARCHAR(64) → VARCHAR(128)兼容, 可执行
整数类型兼容升级低INT → BIGINT / SMALLINT → INT安全升级, 可执行
nullable → NOT NULL中字段变必填需要先填默认值, 否则报错
NOT NULL → nullable低字段变可选兼容, 可执行
default 变化中DEFAULT 0 → DEFAULT NULL已有行不受影响, 新行行为变
PRIMARY KEY 变化高主键变更影响查询计划, DBA 必须 review
COMMENT 变化低注释文字变更无影响, 可执行

3.3 大表 DDL 防呆

提交时如果表行数 > 10 万 或 数据 > 100MB (阈值可在 settings 配), 弹出"大表 DDL 防呆"对话框:

⚠️ 大表 DDL 防呆弹窗
⚠️ 检测到大表 DDL
表 accesscard_black_detail: 1,256,890 行 / 856 MB (阈值 10万行 / 100MB)
直接执行会锁表 ~30 秒, 业务会感知。请选择:
🛡️ 启用 gh-ost (DBA 兜底) · 推荐 ⚡ 立即执行 (双层 confirm 锁表) ✖ 终止工单
DBA 兜底说明: 业务 RD 漏勾 gh-ost 时, DBA 在详情页可一键启用。
✓

业务 RD 三种选择: ① 启用 gh-ost (推荐) — 勾上后审批通过会走 gh-ost, 不锁表 ② 立即执行 — 紧急情况下, 双层 confirm 后直接锁表执行 (DBA 会收到钉钉) ③ 终止工单 — 不该改, 取消

4.3 失败时怎么办

⚠

看到红色失败提示, 先看 error_message 字段 (在进度面板底部), 常见失败原因和应对:

失败现象可能原因怎么应对
连接 MySQL 失败实例凭据失效 / 网络不通联系 DBA 检查实例配置
row count 0 / too small表是空的, gh-ost 不需要取消, 改走普通 SQL 执行
binlog 格式不是 ROWMySQL binlog_format != ROW联系 DBA 改 binlog_format (5.7+ 默认 ROW)
切流超时 (Cut-over timeout)长事务 / DML 阻塞重试, 选业务低峰期执行
GoInception panic: lost connection大表 + MODIFY + bigint→varchar (8/13 教训)走字段 diff 端点旁路, 不依赖 goinception

操作: - 详情页点"取消任务" (clean gh-ost 影子表, 不污染原表) - 修复后点"重试" (复用同一工单, 不用重新走审批) - 实在不行, 详情页找 DBA 兜底 (切回"立即执行"模式, 锁表跑)

4.4 成功后: DDL 智能回滚 (v0.4.5)

DDL 失败时, Archery 自动尝试回滚 (不用你手动):

archery.local/sqlworkflow/detail/12345/ · DDL 智能回滚
🔄 DDL 智能回滚中...
原 DDL: ALTER TABLE t MODIFY COLUMN col VARCHAR(100)
失败原因: gh-ost 切流超时 (Cut-over timeout)
自动回滚 SQL (v0.4.5):
ALTER TABLE t MODIFY COLUMN col VARCHAR(50);
↑ 自动逆向, 把 col 改回原值 (从原始 schema 快照读)
ℹ

支持的智能回滚 (5 种 DDL): ADD COLUMN → DROP, MODIFY → 改回原值, CHANGE → 改回原名, DROP → ADD 回 (从快照), TRUNCATE → 提示备份恢复. 其他不常见 DDL 返 warnings 不自动回滚, 走人工。

06DBA · 字段 diff 兜底

6.1 业务 RD 漏勾 gh-ost 怎么办

业务 RD 提了大表 DDL, 但忘了勾"启用 gh-ost", 走普通 SQL 执行会锁表。DBA 在详情页可以兜底启用:

archery.local/sqlworkflow/detail/12345/ · 大表 alert (DBA 兜底)
⚠️ 大表 DDL · 未启用 gh-ost
表 accesscard_black_detail: 1,256,890 行 / 856 MB
业务 RD 提交时漏勾 gh-ost, 当前配置会锁表 30s。DBA 可兜底:
🛠️ DBA 兜底启用 gh-ost ⚡ 强制立即执行 (双层 confirm)
↑ DBA 兜底启用后, 审批通过会改走 gh-ost 跑, 不锁表。

6.2 三路径选择 (DBA 视角)

场景DBA 操作效果
业务 RD 漏勾, 表大需要 gh-ost 点 "🛠️ DBA 兜底启用 gh-ost" 工单 enable_gh_ost 字段置 true, 审批通过走 gh-ost
业务 RD 否决 gh-ost (觉得不必要), 但实际该用 先点 "✖ 取消 task + ⚡ 立即执行" 取消原 task, 业务 RD 重新提交"立即执行"工单
真紧急, 表小不需要 gh-ost 点 "⚡ 强制立即执行" 双层 confirm 后, 普通 SQL 执行 (锁表)

7.2 触发空 alter 的 SQL (3 决策落地)

v0.4.5 拍板 3 决策 (8/13): 用 ENGINE=InnoDB, ROW_FORMAT=<原值>, DEFAULT CHARACTER SET=<原值> COLLATE=<原值> 触发整表物理页重写。

触发后: 生成的 alter 子句
原表: accesscard_black_detail (utf8mb4 / utf8mb4_general_ci / DYNAMIC)
生成的触发 alter (3 层防护):
ALTER TABLE accesscard_black_detail ENGINE=InnoDB ROW_FORMAT=DYNAMIC DEFAULT CHARACTER SET=utf8mb4 COLLATE=utf8mb4_general_ci;
↑ 3 层防护: ENGINE 触发重写 + ROW_FORMAT 防丢失 + CHARSET 强一致
↑ 走 gh-ost 异步执行, 不锁表, 业务零感知

08权限配置 (DBA 在 admin)

8.1 4 个 perm 自动注册

Django admin 会自动给 DdlGhostTask model 注册 4 个标准 perm, 0 业务代码改动:

Perm用途谁有 (默认)
view_ddlghosttask看菜单 + 任务管理列表 + 详情DBA + admin (DBA 手动勾)
add_ddlghosttask建任务 (一般自动建, 不用手)仅 DBA + admin
change_ddlghosttask取消 / 重试 / 回滚 + 操作端点仅 DBA + admin
delete_ddlghosttask删任务 (清理历史)仅 DBA + admin

8.2 DBA 在 admin 后台配置

archery.local/admin/auth/group/
认证和授权 → 组
"DBA" 组 ✓ view_ddlghosttask ✓ add_ddlghosttask ✓ change_ddlghosttask ✓ delete_ddlghosttask
"DBA组长" 组 跟 DBA 一样 (4 个 perm 全勾)
"业务RD组长" 组 ✓ view_ddlghosttask 其他 3 个不勾 (只能看, 不能改)
"业务RD" 组 不勾任何 (业务 RD 默认看不到 gh-ost 任务管理菜单)
💡

8/13 教训: 默认权限最小化: 业务 RD 普通用户默认不勾任何 gh-ost perm, 业务 RD 组长可勾 view (只能看, 不能改)。 取消/重试/回滚 3 个操作端点 0 业务代码改动做 perm 守卫 (跟 view 一套机制)。

09常见问题 FAQ

Q1: 我提 DDL 时没看到字段 diff 检测面板, 怎么回事?
字段 diff 检测只在 ALTER TABLE 类 DDL 自动触发。如果你的 SQL 是 CREATE TABLE / DROP TABLE / SELECT, 不会触发 (因为没有"原字段定义"可比)。
Q2: 字段 diff 提示"字符集变化: utf8mb4 → utf8", 我没改字符集啊?
这是 11 条规则里的最坑规则。你写 DDL 时没带 CHARACTER SET utf8mb4, Archery 默认按"目标字段定义"解析 (可能是 utf8 或空)。 修法: 点"📋 复制补全 SQL"按钮, Archery 会生成"强制带原 CHARSET + COLLATE"的 DDL, 避免索引失效。
Q3: 我勾了"启用 gh-ost", 但审批通过后还是直接执行了, 没用 gh-ost
两种可能: ① 表很小 (行数 < 1 万), gh-ost 不划算, 系统自动跳过走普通执行 ② 审批人勾掉了 (DBA 觉得不必要), 跟审批人确认 ③ gh-ost 二进制没装, 联系 DBA 检查 /opt/archery/bin/gh-ost
Q4: gh-ost 跑到一半卡住 / 失败, 业务会受影响吗?
不会。gh-ost 的核心特性就是"不锁表", 它建影子表 + 同步 binlog, 即使失败也是影子表, 原表数据完整。 修法: 详情页点"取消任务"清理影子表, 修复后重试。
Q5: 我是大表 DDL, 提交时没看到"大表防呆"弹窗, 为什么?
阈值默认行数 10 万 / 大小 100MB, 在 settings.CUSTOM_BIG_TABLE_ROW_THRESHOLD 和 CUSTOM_BIG_TABLE_SIZE_THRESHOLD_MB 配。 如果你的表 < 10 万行, 不触发防呆是正常的 (不需要 gh-ost)。如果你的表 > 10 万行还没弹, 联系 DBA 检查阈值配。
Q6: gh-ost 切流 (Cut-over) 超时, 怎么重试?
详情页点"🔄 重试"按钮 (跟原工单绑定, 不用重走审批)。 切流超时通常因为: ① 业务高峰期有长事务 / 大 DML ② binlog 同步堆积 建议: 选业务低峰期 (深夜 / 周末) 重试, 或联系 DBA 临时 set gh-ost chunk-size=2000。
Q7: 字段 diff 提示"高风险: 字符集变化", 但我就是要改字符集, 怎么办?
这是 8/13 生产事故根因, 强烈不建议改字符集。 如果业务真需要 (比如从 utf8 升 utf8mb4), 走以下流程: ① 先在测试库跑 ② 用 gh-ost 跑 (不锁表) ③ 选业务低峰期 ④ 准备回滚 SQL (改回原字符集) ⑤ 通知 DBA 现场待命
Q8: DDL 智能回滚触发, 我要拒绝回滚吗?
不要。智能回滚 (v0.4.5) 是把已变更的字段改回原值, 避免"半残状态"。 如果你回滚会导致数据丢失 (比如 ADD COLUMN 已经有新数据), 系统会检测到, 返 warnings 让你确认。
Q9: 我是业务 RD, 怎么在任务管理列表看自己提的任务?
两种方式: ① 详情页直接访问 /gh_ost/progress/<workflow_id>/ (你提的工单都能看) ② 申请 view_ddlghosttask perm (DBA 在 admin 后台勾给"业务RD组长"组), 列表里只看自己提的
Q10: 业务 RD 漏勾 gh-ost, 工单已经审批通过了, 还有救吗?
有。详情页有"🛠️ DBA 兜底启用 gh-ost"按钮, DBA 点击后工单改走 gh-ost 重跑 (复用原审批)。 紧急情况下, 详情页"⚡ 立即执行"按钮, 双层 confirm 后直接锁表跑。

10业务场景案例 (4 个真实)

📌 案例 1: 业务 RD 提大表 DDL, 字段 diff 提示字符集丢失

背景: 张三 8/13 提 ALTER TABLE accesscard_black_detail MODIFY COLUMN card_no VARCHAR(64) (大表, 120 万行)

Archery 检测: 字段 diff 显示"字符集变化: utf8mb4 → utf8, 跨表 JOIN 索引可能失效"

张三 操作: 点"📋 复制补全 SQL", 生成 ALTER TABLE ... VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci, 提交

结果: 审批通过, 走 gh-ost 跑 3 分钟, 业务零感知, 索引没失效

教训: 字符集没带会跨表 JOIN 索引失效 (8/13 生产事故根因, 11 条规则重点防护)

📌 案例 2: 业务 RD 漏勾 gh-ost, DBA 兜底

背景: 李四 8/15 紧急修复上线, 提了 ALTER TABLE log_record ADD INDEX idx_xxx, 大表 80 万行, 没勾 gh-ost

DBA 收到工单: 详情页大表 alert 弹出"未启用 gh-ost", 决定兜底

DBA 操作: 点"🛠️ DBA 兜底启用 gh-ost"按钮, 工单自动改走 gh-ost

结果: 审批通过, gh-ost 跑 4 分钟, 业务零感知

教训: 紧急情况下业务 RD 容易漏勾, DBA 兜底是最后一道防线

📌 案例 3: gh-ost 切流超时, 智能回滚兜底

背景: 王五 8/19 业务高峰期提了 MODIFY COLUMN bigint → varchar (大表, 业务低峰期踩点失败)

gh-ost 切流超时: 一直有 DML 阻塞, 切流 30 分钟没成功

详情页提示: "切流超时, 失败, 触发智能回滚"

v0.4.5 智能回滚: 自动生成 MODIFY COLUMN col bigint 改回原值, 跑成功

结果: 业务表回到原状态, 没用 gh-ost 切流, 工单标 failed 但不留半残

教训: 选业务低峰期; 智能回滚 5 种 DDL 全覆盖, 不用 DBA 手动

📌 案例 4: DBA 兜底定期碎片回收

背景: 134 dev 业务库 8/20 健康检查发现 accesscard_black_detail 碎片率 42% (DATA_FREE 38GB), MySQL 5.7 走 OPTIMIZE TABLE 会锁表

DBA 决定: 用 v0.4.5 碎片回收, 走 gh-ost 不锁表

DBA 操作: 134 dev 访问 /gh_ost/rebuild/list/ → 选 3 张表 → 点"一键回收"

触发空 alter: ENGINE=InnoDB ROW_FORMAT=DYNAMIC DEFAULT CHARACTER SET=utf8mb4 COLLATE=utf8mb4_general_ci

结果: gh-ost 异步跑 8 分钟, 碎片归零, 业务零感知, DdlGhostTask 记 rebuilt_* 字段

教训: 8/13 拍板 ENGINE+ROW_FORMAT+CHARSET 3 层防护, 0 风险飘字段
